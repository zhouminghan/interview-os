# 面试官原问题

> 比如订单流，它可能会做一些状态变更，还需要和别的表做关联，类似这种场景有没有遇到过？

后续追问：

> 交易场景一般会采用什么方式？窗口还是 TTL？

> 你为什么第一时间想到状态外置，而不是用 Flink 自身的状态？

---

# 这个问题考察什么？

这个问题其实是在判断：

1. 你有没有真正理解 Flink 状态机制。
2. 你是否区分实时计算中的：

   * 流流 Join
   * 流表 Join
   * 维度关联
3. 你有没有考虑实时业务中的数据变化问题。

---

# 你的原回答评价

你的回答思路：

> 如果订单状态变化，可以把维度放 HBase/Redis，通过监听变化清理缓存或者 Flink 状态。

这个方向有一定合理性。

但是存在一个问题：

你把**订单状态变化问题**和**维度变化问题**混合了。

订单状态：

例如：

```
订单创建
订单支付
订单完成
订单退款
```

它本身属于事实流。

用户：

```
用户等级
用户地区
会员状态
```

才更像维度。

所以面试时需要更加严谨。

# 标准回答

## 第一部分：先判断 Join 类型

回答：

> 这个问题首先需要看业务场景，因为实时 Join 不是一种固定方案。

主要分三类：

---

## 场景1：流和维度表 Join

例如：

订单流：

```
order_id
user_id
amount
```

关联：

用户维度：

```
user_id
level
province
```

这种场景：

维度变化频率低。

一般：

### 方案1：Broadcast State

适合：

小维表。

流程：

```
MySQL维表

      ↓

Flink Broadcast State


订单流

      ↓

Flink Join

      ↓

结果
```

优点：

* 查询快
* 不依赖外部系统

缺点：

* 维表过大会导致Task状态膨胀。

---

### 方案2：Async IO 查询外部存储

例如：

Redis

HBase

MySQL

流程：

```
订单流

 ↓

Async Lookup

 ↓

Redis/HBase

 ↓

Join结果
```

适合：

维表比较大。

---

# 场景2：双流 Join

例如：

订单支付流：

```
order_id
pay_time
```

订单创建流：

```
order_id
create_time
```

两个都是实时流。

这个时候：

不能无限等待。

因为：

订单创建可能来了。

支付可能：

10分钟后

1小时后

甚至第二天。

所以需要：

---

## 方案1：窗口 Join

例如：

10分钟窗口。

逻辑：

```
创建订单

        +
支付事件

        ↓

10分钟窗口内匹配
```

适合：

业务允许时间范围。

例如：

用户点击和曝光关联。

---

## 方案2：Interval Join

Flink提供：

Interval Join。

例如：

订单创建时间：

T

支付时间：

T+0~24小时

允许：

```
create_time <= pay_time <= create_time+24h
```

适合交易场景。

---

# 场景3：复杂状态计算

例如：

订单生命周期：

```
创建

↓

支付

↓

发货

↓

完成
```

需要保存订单当前状态。

这个时候：

Flink State 更合适。

---

# 为什么不是全部放 Flink State？

这里是面试重点。

你的原回答需要优化。

正确回答：

> Flink State本身非常适合短周期计算和实时状态管理，但是是否使用它，需要看状态生命周期和业务访问需求。

---

## Flink State适合：

### 1. 临时计算状态

例如：

窗口聚合：

```
5分钟UV
```

状态：

保存5分钟。

---

### 2. 流程状态

例如：

订单等待支付。

等待：

30分钟。

---

## 不适合：

长期业务状态。

例如：

用户画像：

```
用户历史消费金额
用户等级
会员状态
```

保存几年。

如果全部放Flink State：

问题：

### 1. State越来越大

Checkpoint压力增加。

### 2. 运维复杂

状态恢复时间变长。

### 3. 多业务访问困难

其他系统无法直接查询。

---

所以：

长期业务状态：

更适合：

* MySQL
* HBase
* Redis
* Iceberg

---

# 如果结合你的频道业务回答

你的项目不是交易，所以可以这样说：

> 我们频道业务主要是流量类数据，没有复杂交易状态流，所以主要场景是日志流和业务维度关联。

例如：

日志：

```
用户点击事件
```

关联：

频道维度：

```
频道类型
频道等级
频道属性
```

这种场景：

小维表：

Broadcast State。

变化较少。

如果维度变化：

通过维表更新通知：

刷新广播状态。

# 如果面试官继续问：

## Flink状态如何清理？

回答：

> Flink State一般通过TTL机制管理生命周期。

例如：

```
state.ttl=24h
```

超过时间：

自动清理。

但是：

TTL主要解决状态生命周期问题。

它不能解决：

业务数据长期存储需求。

# 技术自检

这里纠正几个容易错误：

---

## ❌ 错误说法

> Redis一定比Flink State快。

不严谨。

原因：

Flink State在本地访问，可能更快。

---

## ❌ 错误说法

> 所有维表Join都用Broadcast Join。

错误。

大维表广播会导致：

TaskManager内存压力。

---

## ❌ 错误说法

> TTL可以保证数据一致性。

错误。

TTL只是生命周期管理。
