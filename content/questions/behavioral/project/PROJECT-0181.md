**一、面试官真正想考什么？**

不是问你有多大数据量（这个只是背景），而是考：
- 你对大规模数据处理的工程能力
- 你是否有体系化的稳定性保障思路
- 你能否从预防→监控→应急三个维度回答

**二、回答思路**

三层保障：事前预防 → 事中监控 → 事后应急

**三、参考答案（面试标准版）**

> 控制在2分钟

百亿级任务稳定性，我们从三个层面保障：

**第一层：事前预防（设计层面）**
- 任务拆分：不做"一个SQL干所有事"，按业务过程拆分独立任务，单任务失败不影响全链路
- 资源隔离：核心任务和探索性任务分Queue，避免资源抢占
- Spark参数标准化：核心任务的executor数量、内存、shuffle分区数有基线配置，不允许随意修改

**第二层：事中监控（运行时）**
- 任务级监控：运行时长超基线X倍报警、数据量波动超阈值报警
- 数据质量监控：核心表配置完整性规则（主键不为空、分区数据量不为0）和波动规则（日环比/周同比超阈值）
- 依赖监控：上游延迟时下游任务不强制触发，避免空跑

**第三层：事后应急（故障处理）**
- 任务失败自动重试（通常配2-3次）
- 数据回溯机制：核心任务支持按分区重跑，幂等设计保证重跑安全
- 值班机制 + 故障定位SOP：看Spark UI → 定位Stage → 分析Task耗时分布 → 确认是倾斜/OOM/依赖问题

**四、技术知识补充**

Spark任务稳定性核心参数：
```text
spark.sql.shuffle.partitions = 2000-5000（百亿级建议）
spark.sql.adaptive.enabled = true（AQE自动调整）
spark.sql.adaptive.skewJoin.enabled = true（倾斜自动处理）
spark.executor.memoryOverhead = 2g+（防止堆外OOM）
spark.maxRemoteBlockSizeFetchToMem = 200m（大Shuffle防OOM）
```

**六、常见错误/踩坑提醒**

- ❌ 「我们数据量很大所以很稳定」（逻辑不通） → ✅ 从预防/监控/应急三层回答
- ❌ 只说监控不说预防 → ✅ 好的架构设计才是稳定性的根本

**七、记忆版（30秒压缩）**

> 三层保障：事前（任务拆分+资源隔离+参数标准化）、事中（时长/质量/依赖三类监控）、事后（自动重试+幂等回溯+定位SOP）。核心理念是好的架构设计比好的监控更重要。
