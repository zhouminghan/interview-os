# 面试官原问题

> 你刚才讲了维度建模，那事实表怎么设计？
> 比如用户行为、帖子消费这种业务，你怎么确定它的粒度？

---

# 一、回答思路

这道题是数仓建模里面非常关键的问题。

很多候选人的回答：

> 根据业务建表，把字段放进去。

这个回答说明只会开发，不懂建模。

面试官真正想考：

1. 你是否理解事实表核心原则。
2. 是否知道粒度为什么重要。
3. 是否能根据业务过程设计模型。
4. 是否考虑后续扩展和指标计算。

核心：

**事实表设计第一原则：先确定业务过程，再确定粒度。**

---

# 二、标准回答开场

> 我设计事实表的时候，第一步不是先考虑字段，而是先明确业务过程和数据粒度。

因为：

粒度决定：

* 一行数据代表什么。
* 后续指标怎么计算。
* 是否会重复计算。

---

# 三、事实表设计流程

---

## 第一步：确定业务过程

例如QQ频道。

业务过程：

用户消费帖子。

拆解：

用户打开帖子：

产生：

曝光事件。

用户点击：

产生：

点击事件。

用户评论：

产生：

互动事件。

这些都是不同业务过程。

---

所以：

不能简单设计：

```text
用户行为表
```

全部塞进去。

应该根据业务过程拆分。

例如：

```
帖子曝光事实表

帖子点击事实表

帖子互动事实表
```

---

# 四、第二步：确定事实表粒度

这是重点。

---

## 什么叫粒度？

简单理解：

> 一行数据代表什么业务含义。

例如：

用户登录事实表。

有两种设计：

---

## 方案1：用户+天粒度

例如：

| user_id | dt         | login_cnt |
| ------- | ---------- | --------- |
| 1001    | 2026-07-16 | 3         |

代表：

一个用户一天登录情况。

优点：

数据量小。

缺点：

无法分析：

具体登录时间。

---

## 方案2：事件粒度

例如：

| user_id | event_time |
| ------- | ---------- |
| 1001    | 10:01      |
| 1001    | 15:20      |

代表：

一次登录事件。

优点：

明细完整。

缺点：

数据量大。

---

选择取决于业务需求。

---

# 五、结合频道业务举例

这是你的优势。

---

## 场景：帖子曝光

业务：

分析：

* 哪些帖子热门。
* 用户消费路径。
* 推荐效果。

---

设计事实表：

```sql
dwd_post_exposure_di
```

粒度：

> 一次帖子曝光事件。

字段：

```text
user_id

post_id

channel_id

device

event_time

source
```

---

为什么？

因为后续可以计算：

曝光次数：

```sql
count(*)
```

UV：

```sql
count(distinct user_id)
```

点击率：

```text
点击次数 / 曝光次数
```

---

如果一开始设计：

用户+天粒度。

后面想分析：

某个小时热点。

数据已经丢失。

---

# 六、事实表分类

高级回答可以补充。

通常事实表有：

---

# 1. 事务事实表

记录一次业务事件。

例如：

用户点击。

订单支付。

特点：

一行一个事件。

---

# 2. 周期快照事实表

记录周期状态。

例如：

每天用户活跃情况。

粒度：

用户+天。

---

# 3. 累积快照事实表

记录业务生命周期。

例如：

订单流程：

创建：

支付：

发货：

完成。

一行记录整个生命周期。

---

# 七、事实表设计注意事项

---

## 1. 避免粒度混乱

错误：

一张表：

同时存：

帖子曝光。

帖子评论。

帖子点赞。

为什么？

三个事件粒度不同。

可能：

曝光1次。

点赞0次。

评论10次。

join后容易：

数据膨胀。

---

## 2. 保持事实不可变

例如：

曝光事件发生后。

一般不会修改。

方便：

历史分析。

---

## 3. 保留业务主键

例如：

事件ID。

方便：

去重。

追踪。

---

# 八、事实表和维度表如何关联？

回答：

> 事实表保存业务事件，维度表提供分析角度。

例如：

曝光事实：

```
fact_exposure
```

关联：

用户维度：

```
dim_user
```

帖子维度：

```
dim_post
```

时间维度：

```
dim_date
```

形成：

分析模型。

# 九、结合你的QQ频道项目回答版本

面试可以这样说：

> 以频道内容消费为例，我们首先确定业务过程，比如帖子曝光、点击、互动。
>
> 对曝光行为，我们设计DWD帖子曝光事实表，粒度定义为一次曝光事件。
>
> 因为后续业务需要分析曝光PV、曝光UV、点击率以及不同用户、频道、帖子维度下的消费情况，所以需要保留明细粒度。
>
> 在上层DWS再根据不同分析场景沉淀用户天级活跃、内容消费汇总等公共指标。
>
> 这样既保证明细可追溯，也避免所有下游重复扫描明细。

# 十、技术自检

这里几个容易错误。

---

## ❌ 错误：

> 粒度越细越好。

错误。

粒度越细：

数据量越大。

计算成本越高。

需要结合：

业务需求。

查询场景。

---

## ❌ 错误：

> 所有事实表都是DWD明细表。

不准确。

DWS也可能存在事实汇总。

---

## ❌ 错误：

> 一个事实表只能有一个指标。

错误。

事实表可以包含多个相关事实。

例如：

曝光事实：

曝光次数。

停留时长。

点击标识。

# 十一、最终面试版回答（约2分钟）

> 事实表设计我一般遵循先确定业务过程，再确定粒度，然后设计字段。
>
> 首先需要明确这张表描述什么业务事件，比如频道里面帖子曝光、点击、互动属于不同业务过程。
>
> 对于帖子曝光事实表，我会把粒度定义为一次曝光事件，一行代表一次用户对帖子产生的曝光行为。
>
> 这样可以保留完整明细，后续可以灵活计算曝光PV、UV、点击率等指标。
>
> 如果业务只需要统计每天用户活跃情况，也可以建设用户+天粒度的周期快照表，减少数据量。
>
> 所以事实表设计的核心不是字段多少，而是明确业务含义和粒度，避免粒度混乱导致数据重复或者指标不准确。
