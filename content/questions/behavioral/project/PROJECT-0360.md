# 标准回答（求职者视角）

> 我们频道业务最开始主要还是离线数仓，指标基本都是 T+1 产出。
>
> 但是随着业务发展，比如运营活动、内容消费、用户行为分析等场景，对数据时效性的要求越来越高，所以我们建设了一套实时数仓，把部分核心指标从 T+1 提升到分钟级。

# 一、整体架构介绍

> 整体架构主要是 Kafka + Flink + Iceberg。

链路如下：

```
业务埋点日志

      ↓

Kafka

      ↓

Flink实时计算

      ↓

Iceberg实时明细/汇总表

      ↓

ADS实时指标

      ↓

实时看板
```

---

## 1. Kafka：数据采集层

> 首先业务日志通过埋点系统进入 Kafka。

这里补充业务背景：

> 因为频道业务实际上挂在手Q基础日志体系下面，一个日志 Topic 里面包含多个业务的数据。

比如：

* QQ频道
* QQ群
* QQ空间

多个业务混在一起。

---

## 2. Flink：实时计算层

> Flink主要负责实时数据加工。

包括：

* 数据清洗
* 字段转换
* 业务过滤
* 维度关联
* 实时聚合

---

# 重点讲你的亮点：广播流分流

这里是你的项目特色。

可以这样回答：

> 我们当时一个比较典型的场景是业务日志分流。

因为：

Kafka里面：

```
手Q统一日志Topic

      |
      |
      |
多个业务日志
```

如果直接硬编码：

```
if page_id=x
属于频道
```

后续业务变化维护成本比较高。

所以：

我们维护了一张业务映射维表。

例如：

MySQL：

| page_id | 业务  |
| ------- | --- |
| 1001    | 频道  |
| 2001    | QQ群 |

然后：

Flink读取MySQL维表。

通过 Broadcast State 广播到所有Task。

实现：

```
Kafka日志流

      +

业务映射广播流

      ↓

Flink Join

      ↓

频道业务数据
```

---

# 为什么用广播流？

回答：

> 因为这张业务映射表数据量比较小，而且变化频率相对较低，所以适合广播到Task本地，避免频繁访问外部存储。

同时：

> 后续新增页面或者业务变化，只需要修改维表，不需要重新发布Flink任务，提高了扩展性。

---

# 3. Iceberg：数据湖存储

> Flink处理后的数据我们写入Iceberg。

为什么选择Iceberg？

回答：

主要考虑几个方面：

---

## （1）事务能力

传统Hive表：

* 不支持ACID
* 并发写能力弱

Iceberg：

支持：

* Snapshot
* Schema Evolution
* Atomic Commit

更适合实时写入场景。

---

## （2）实时离线统一

这是重点。

> 因为Iceberg本身支持批流统一，所以实时数据和离线数据可以基于同一份数据资产进行管理。

# 二、实时和离线如何保证口径一致？

这是面试重点。

你的原回答：

> 实时复刻离线逻辑。

方向正确。

但是需要展开。

---

## 第一层：统一业务口径

回答：

> 首先最重要的是指标定义统一。

比如登录UV。

不能：

实时：

```
count(user_id)
```

离线：

```
count(distinct user_id)
```

这样一定会产生差异。

所以：

指标定义、过滤条件、维度范围需要统一。

---

## 第二层：统一模型设计

例如：

离线：

```
ODS

↓

DWD

↓

DWS

↓

ADS
```

实时：

```
Kafka

↓

Flink

↓

实时DWD

↓

实时DWS

↓

实时ADS
```

两边：

* 字段设计一致
* 业务逻辑一致
* 粒度一致

---

## 第三层：代码逻辑复用

高级一点：

> 我们尽量避免实时和离线分别维护两套完全独立逻辑。

例如：

同一个指标：

登录UV

统一定义：

```
用户ID
事件类型
时间范围
过滤条件
```

实时：

Flink SQL实现。

离线：

Spark SQL实现。

逻辑保持一致。

---

## 第四层：数据校验

上线后：

进行：

### 数据量校验

例如：

实时当天累计：

```
100万
```

离线T+1：

```
102万
```

差异需要分析。

---

### 指标校验

例如：

实时：

```
登录UV
```

离线：

```
登录UV
```

每日核对。

# 四、如果面试官追问：Flink如何保证Exactly Once？

回答：

> Flink主要通过Checkpoint机制实现Exactly Once。

流程：

```
Source

↓

Checkpoint Barrier

↓

Operator State Snapshot

↓

Sink提交事务
```

如果任务失败：

恢复最近一次Checkpoint。

避免重复计算。

对于Kafka：

依靠：

* Kafka Offset管理

对于Iceberg：

依靠：

* Flink两阶段提交

---

# 五、技术正确性检查

你的原回答：

> SBO表支持事务，Flink精准一次性保证数据不丢不重复。

这里需要注意。

“Flink精准一次性保证数据不丢不重复”这个表达不够严谨。

更准确：

Flink提供 Exactly Once 语义能力，但是否端到端 Exactly Once，需要看：

* Source是否支持事务
* Sink是否支持事务提交

例如：

Kafka：

支持。

Iceberg：

支持事务提交。

所以才可以做到端到端一致。
