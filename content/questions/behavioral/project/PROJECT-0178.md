**一、面试官真正想考什么？**

不是要项目流水账，而是考：
- 你对整体架构是否清楚（全景视角）
- 你能否分层讲清楚每层解决什么问题
- 你是真参与还是"打杂跑SQL"

**二、回答思路**

业务背景（15秒）→ 架构全景（30秒）→ 每层设计要点（60秒）→ 我的核心贡献（30秒）

**三、参考答案（面试标准版）**

> 控制在2-3分钟

**业务背景：** QQ频道是手Q体系下的社交产品，类似Discord的社区形态。我们负责频道业务域的数据建设，覆盖内容、互动、增长三个方向，核心日志达百亿级/天。

**整体架构：**
```text
数据源 → ODS（原始日志接入）→ DWD（明细事实层）→ DWS（公共汇总层）→ ADS（应用服务层）
         离线：手Q公共日志 + 业务库
         实时：Kafka → Flink → Iceberg
```

**每层设计要点：**

- **ODS层：** 核心挑战是频道数据嵌套在手Q公共日志里，需要动态分流。用Flink广播流 + 配置化维表实现业务隔离。
- **DWD层：** 标准化是核心目标。按业务过程建事实表（曝光事实、点击事实、内容发布事实等），保持事实和维度分离——因为频道是社交业务，用户画像、频道标签等维度变化快，不在DWD做大量退化。
- **DWS层：** 按主题域沉淀公共指标。主题域包括用户域、内容域、互动域、推荐域（流量域）。关联维度在这层完成，保证分析效率和指标复用。
- **ADS层：** 面向运营看板和分析报表，按具体业务需求聚合。

**我的核心贡献：** 负责内容域和互动域的DWD/DWS层建设，管理50-60张核心表，参与Spark性能优化和元数据治理。

**四、技术知识补充**

为什么频道不做DWD维度退化（与电商的区别）：
- 电商：商品属性相对稳定，退化到事实表可以减少Join，提高查询效率
- 频道：频道标签、用户画像、推荐特征变化快，退化后更新成本极高
- 设计原则：DWD保证标准统一（变化被限制在这一层），DWS保证分析效率（在这里做维度关联）

**五、追问预判**

1. **追问：主题域怎么划分的？依据是什么？**
   → 按业务过程划分：用户域（注册/活跃/留存）、内容域（发布/曝光/消费）、互动域（点赞/评论/分享）、推荐域（曝光/点击/转化）。依据是业务方的分析需求边界。

2. **追问：50-60张表怎么管理？**
   → 表级元数据规范（命名/分区/字段标准）+ 血缘关系维护 + 数据质量监控（完整性/时效性/波动告警）。

3. **追问：离线和实时怎么协作？**
   → 实时链路做核心指标的分钟级输出（通过Flink + Iceberg），离线做全量数据的T+1加工。两套链路在DWS层对齐指标口径，避免"实时一个数、离线一个数"。

**六、常见错误/踩坑提醒**

- ❌ 先讲10分钟背景（公司/部门/老板） → ✅ 15秒背景直接进架构
- ❌ 「我们用了Hive、Spark、Kafka、Flink...」（罗列技术栈） → ✅ 每个技术点说明解决什么问题
- ❌ 把"跑SQL"说成"负责建设" → ✅ 明确说自己设计了什么、推动了什么
