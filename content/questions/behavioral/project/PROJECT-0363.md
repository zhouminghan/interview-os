# 面试官原问题

> 元数据治理这块，我理解是一些规范治理是吧？
> 这种治理工作你们是怎么推进的？

> 因为只能说，你没有办法当做一个专项来做处理。历史的一些表可能不符合规范，但是又要继续使用，这种怎么处理？

---

# 一、回答思路

这道题其实是 Q8 的深入追问。

面试官关注的不是：

“你知道什么叫元数据。”

而是想确认：

1. 你有没有参与过真实治理。
2. 你理解存量系统治理难点。
3. 你有没有工程上的权衡意识。

很多新人会回答：

> 把历史表全部改成规范。

这个回答在生产环境通常是不现实的。

原因：

数仓里面一张核心表可能有：

* 几十个下游任务
* 几百个指标依赖
* BI看板依赖
* 运营分析依赖

贸然修改容易造成大面积影响。

---

# 二、标准回答（求职者视角）

> 元数据治理我们当时没有采用一次性大改的方式，因为频道业务本身已经运行多年，历史资产比较多，如果直接按照新规范全部重构，影响范围会比较大。

> 所以我们的治理策略主要是：
>
> **存量兼容治理，新建严格治理。**

---

# 三、第一部分：新建表严格治理

回答：

> 对于新增的数据资产，我们会要求按照规范建设。

主要包括：

---

## 1. 表命名规范

例如：

按照：

```
分层_业务域_主题域_业务含义_粒度
```

例如：

```
dwd_channel_user_action_di
```

能够体现：

* 分层
* 业务范围
* 数据粒度

---

## 2. 主题域归属

例如频道业务：

可能划分：

* 用户域
* 内容域
* 互动域
* 推荐域

新建表必须明确属于哪个主题域。

作用：

后续：

* 查找方便
* 血缘清晰
* 资产管理方便

---

## 3. 字段标准

例如：

统一：

用户标识：

```sql
user_id
```

时间：

```sql
create_time
```

避免：

同一个业务概念：

多个字段名称。

---

## 4. 指标标准

比如：

登录UV。

统一：

定义：

```
统计周期
统计对象
过滤条件
计算方式
数据来源
```

避免不同团队重复建设。

---

# 四、第二部分：历史表如何治理？

这是重点。

回答：

> 对于历史表，我们不会直接修改结构，而是通过兼容方式逐步治理。

主要几个方向。

---

# 1. 补充元数据

历史表可能：

表名不规范。

例如：

```
login_table
```

但是业务上：

它属于：

用户行为域。

那么我们会补充：

* 表描述
* 业务域
* 主题域
* 负责人
* 使用说明

让使用者知道：

这张表是什么。

---

# 2. 血缘梳理

通过血缘关系分析：

例如：

```
ODS
 ↓
DWD
 ↓
DWS
 ↓
ADS
```

明确：

* 上游来源
* 下游影响

避免：

不知道谁依赖这张表。

---

# 3. 渐进式替换

如果历史表确实问题比较大。

例如：

字段混乱。

那么不会直接修改。

而是：

建立新表：

```
旧表

↓

规范新表

↓

逐步迁移下游
```

等：

* 下游迁移完成
* 验证数据一致

再下线旧表。

---

# 五、为什么不能直接改历史表？

这个需要重点说。

回答：

> 因为数据仓库里面表不仅仅是一份数据，它实际上是一份被大量业务依赖的数据资产。

例如：

一个核心DWD登录表。

可能被：

* 运营报表
* 推荐分析
* 用户分析
* 实验平台

几十个任务引用。

如果直接修改：

可能出现：

---

## 1. 字段变化影响

例如：

删除字段：

```sql
user_type
```

下游：

```sql
select user_type
```

直接失败。

---

## 2. 口径变化影响

例如：

UV定义变化。

以前：

```sql
count(user_id)
```

现在：

```sql
count(distinct user_id)
```

虽然字段没变。

但是业务结果变了。

---

## 3. 数据回溯风险

历史数据重新加工：

可能导致：

* 下游指标变化
* 报表变化
* 业务误判

---

所以：

生产环境治理一定需要：

影响评估。

---

# 六、结合你的项目补充

你的项目里面还有一个亮点：

数据中台强制规范。

可以这样回答：

> 后续随着数据中台能力建设，我们也逐步把一些规范前置到开发流程里面。

例如：

建表的时候：

要求填写：

* 业务域
* 主题域
* 表负责人
* 数据用途

平台自动生成：

部分命名规范。

这样治理从：

人工检查

变成：

系统约束。

这个回答比较像大厂实践。

# 七、技术自检

这里有几个容易错误的地方。

---

## ❌ 不建议说：

> 元数据治理就是表命名规范。

太浅。

元数据包括：

技术元数据：

* 表
* 字段
* 分区
* 血缘

业务元数据：

* 指标
* 业务定义

管理元数据：

* Owner
* 权限
* 生命周期

---

## ❌ 不建议说：

> 历史表全部重构。

大型公司基本不会这么干。

---

## ❌ 不建议说：

> 修改字段不会影响下游，因为Hive字段可以兼容。

错误。

尤其：

删除字段、类型变化、语义变化都会影响。

---

# 八、面试评分

你的原回答：

真实度：
⭐⭐⭐⭐⭐

治理经验：
⭐⭐⭐⭐

不足：

表达偏口语：

例如：

> 老表就不要动。

需要升级成：

> 存量资产采用兼容治理，通过血缘和影响评估逐步迁移。

这样从开发视角提升到架构视角。

# 九、最终面试版（1分钟）

> 我们元数据治理主要采取增量治理和存量治理结合的方式。
>
> 新建表严格执行规范，包括业务域、主题域、表命名、字段标准和指标定义。
>
> 对历史表，由于已经存在大量上下游依赖，不会直接修改，而是先补充元数据，包括业务描述、Owner、主题域归属和血缘关系。
>
> 如果历史表确实存在较大问题，会采用新建规范表、逐步迁移下游的方式治理。
>
> 因为数据仓库里面核心表本质上是数据资产，任何结构或者口径变化都需要评估影响范围，不能为了规范影响线上业务。

这个回答比较符合 **4年以上大数据开发向高级数仓开发转型** 的定位。
