# Q5 面试官原问题

> 那你们让 AI 敲完代码之后，在测试的时候会怎么去做数据的测试？

（结合上下文，面试官其实想进一步探查：）

1. AI 生成代码以后，如何保证正确性？
2. 数据开发不是代码生成问题，而是数据质量问题，你有没有意识？
3. 有没有完整的数据研发流程？
4. AI 在生产环境有没有闭环？

# 回答思路

这个问题不要只回答：

> AI生成SQL，然后人工测试。

这个层次比较浅。

优秀的大数据开发回答应该体现：

**AI 提效 ≠ AI 替代开发**

数据开发核心风险：

* SQL语法正确
* 业务口径正确
* 数据链路正确
* 数据质量稳定
* 上下游影响可控

所以回答结构：

```
1. AI生成只是第一阶段
2. 我们需要增加数据验证闭环
3. 从数据量、一致性、业务维度、异常检测几个方向验证
4. 最终人工review上线
```

---

# 标准回答（求职者视角）

> 这个其实我们内部也比较关注，因为数据开发和普通代码开发不太一样。
>
> 普通代码可能更多关注功能正确，但是数据开发更关注数据结果是否符合业务预期。
>
> 所以目前我们的方式并不是让 AI 直接生成之后就上线，而是增加了一层数据验证流程。

---

## 第一部分：开发阶段验证

> 首先在 AI 生成 SQL 或者加工逻辑之后，我们会先让 AI 根据需求生成对应的数据验证方案。

例如：

> 假设我们新增一个登录 UV 指标。

我们不会只看 SQL 能不能执行，而是会验证：

### 1. 数据量级校验

比如：

```
ODS登录日志数量
 ↓
DWD登录明细数量
 ↓
DWS聚合数量
 ↓
ADS指标数量
```

逐层比对。

例如：

* ODS 有100万条
* DWD加工后应该保持合理范围

如果突然：

* ODS 100万
* DWD只有10万

说明可能存在过滤逻辑或者关联问题。

---

### 2. 指标一致性校验

比如：

登录 UV 指标。

我们会验证：

新开发指标

vs

已有历史指标

例如：

```
select count(distinct user_id)
```

和

原指标口径计算结果

进行对比。

如果差异超过阈值，需要进一步确认：

* 业务口径变化？
* SQL逻辑问题？
* 数据源异常？

---

### 3. 维度拆分验证

因为很多数据问题整体看不出来。

所以会进一步拆维度。

例如：

登录 UV：

整体：

```
100万
```

拆：

```
Android
IOS
PC
```

或者：

```
国内
海外
```

观察是否存在异常波动。

---

## 第二部分：上线后的质量监控

> 上线之后，我们会结合已有的数据质量体系进行监控。

主要包括：

### 完整性

例如：

分区是否正常产生。

```
dt='2026-07-16'
```

是否存在。

---

### 空值检测

例如：

核心字段：

```
user_id
channel_id
event_time
```

不应该大量为空。

---

### 波动检测

例如：

日报指标：

```
今日UV
昨天UV
```

计算：

```
(today-yesterday)/yesterday
```

如果超过阈值报警。

---

### 业务规则校验

比如：

频道业务：

帖子数不应该突然变成0。

或者：

新增用户不应该突然下降90%。

这种属于业务合理性检测。

---

## 第三部分：AI参与的数据质量提升

这里结合你的AI项目，会更加高级。

> 后续我们也尝试让 AI 参与数据验证过程。

例如：

以前：

开发人员自己写校验SQL。

现在：

AI根据：

* 表结构
* 指标定义
* 血缘关系
* 历史规则

自动生成：

* 数据校验SQL
* 检查项
* 风险报告

比如：

一个ADS指标上线。

AI可以自动分析：

```
ADS指标
 |
DWS
 |
DWD
 |
ODS
```

然后生成：

* 上游数据量检查
* 字段空值检查
* 指标一致性检查

最后输出一个验证报告。

---

# 最后总结

> 所以整体来说，我们现在的模式还是 AI 辅助开发，而不是完全替代人工。
>
> AI 更适合帮助我们完成重复性的工作，比如 SQL生成、测试SQL生成、影响分析。
>
> 但是业务口径确认、数据质量判断、上线风险评估，目前还是需要开发人员参与。
>
> 我理解未来数据开发人员更多会从代码生产者转向数据方案设计者和质量审核者。

# 技术正确性检查

这个回答整体合理。

但是有几个容易踩坑点：

---

## ⚠️ 不建议说

> AI自动保证数据正确

错误。

原因：

LLM没有真实业务理解能力。

它只能：

* 根据上下文推理
* 根据规则生成

最终正确性仍需要：

* 数据验证
* 人工审核

---

## ⚠️ 不建议说

> AI直接拿生产数据验证

风险：

生产数据敏感。

更合理：

测试环境 / 脱敏数据 / 查询接口。

---

## ⚠️ 你的原回答问题

你原来的回答：

> 让AI生成SQL，然后对ODS、DWD、DWS做核对。

方向对。

但是略显：

“工具使用者”。

缺少：

* 数据质量体系
* 数据研发流程
* 风险控制

面试官听完可能觉得：

你会用AI。

但是不一定觉得：

你理解数据工程。
