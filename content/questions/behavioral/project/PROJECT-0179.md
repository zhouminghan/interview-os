**一、面试官真正想考什么？**

不是要你列清单，而是考：
- 你的真实贡献边界在哪
- 你是执行者还是设计者
- 你有没有超出"写SQL"的能力

**二、回答思路**

分三类说：设计类 → 开发类 → 治理类，体现从设计到落地的完整链路

**三、参考答案（面试标准版）**

> 控制在2分钟

我在QQ频道项目中的工作可以分三类：

**第一类：架构设计。**
- 参与内容域和互动域的主题域划分和建模方案设计
- 设计DWD层事实表结构（按业务过程建表，明确粒度和度量）
- 设计DWS层公共指标（内容消费指标、互动率指标等），确保口径统一

**第二类：核心开发。**
- 负责50-60张核心业务表的ETL开发和维护
- 百亿级日志的Spark任务优化（数据倾斜处理、AQE调参、小文件合并）
- 实时链路参与Flink任务开发（广播流分流方案）

**第三类：治理推动。**
- 元数据治理：推动表命名规范、字段标准、指标口径统一
- 资产治理：通过数据地图和血缘分析，识别僵尸表并推动下线
- 质量治理：建立核心表的完整性、时效性、波动监控规则

**总结一句话：** 从设计到开发到治理，是完整参与的核心成员，不只是"接需求跑SQL"。

**四、技术知识补充**

"50-60张核心表"的构成：
- DWD层：~20张事实表（曝光、点击、内容发布、互动行为等）
- DWS层：~20张汇总表（日/周/月粒度的主题域公共指标）
- 维度表：~10张（频道维度、用户维度、内容类型维度等）
- ADS层：~10张应用表（面向看板）

**五、追问预判**

1. **追问：你说参与设计，是你主导还是协作？**
   → 内容域和互动域的建模方案是我主导设计的，整体数仓架构规划是和组长协作确定的。

2. **追问：你怎么推动治理落地的？困难是什么？**
   → 最大困难是历史表下线。下游依赖不明确时不敢动。解决方式：先建血缘 → 评估影响范围 → 和下游确认 → 设冷冻期 → 最终下线。

3. **追问：治理效果怎么量化？**
   → {需要补充：如"僵尸表下线X张，存储节省X TB，任务数减少X%"}

**六、常见错误/踩坑提醒**

- ❌ 「我负责写SQL和跑数」 → ✅ 从设计、开发、治理三个维度展现完整能力
- ❌ 「我们组长安排我做什么我就做什么」 → ✅ 体现主动性和Owner意识

**七、记忆版（30秒压缩）**

> 三类工作：设计（主题域建模+指标体系）、开发（50-60张核心表+Spark优化+Flink实时）、治理（元数据规范+血缘+资产下线）。从设计到落地完整参与。
