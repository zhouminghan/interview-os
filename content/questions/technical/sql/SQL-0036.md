# 回答思路

1. 开口先复述约束：同一 `Email` 只保留 `Id` 最小的记录，其余记录删除。
2. 接着选确定性写法：用自连接让每条记录和同一 `Email` 下更小的 `Id` 配对，删掉配对命中的记录。
3. 然后检查边界：`Id` 是否唯一、`Email` 是否允许 NULL，以及目标 SQL 引擎是否支持多表 `DELETE`。
4. 最后补落地验证：先 `SELECT` 预览待删行或加事务，再执行删除并确认每个 `Email` 只剩一行。

# 一句话

按 `Email` 分组保留最小 `Id`，用自连接删除「同一 `Email` 下存在更小 `Id`」的那些行。

# 30 秒回答

这题的关键是让每个重复组有一个明确的幸存者。可以把 `Person` 自连接，条件是两边 `Email` 相等且左表 `Id` 更大，那么左表命中的就是需要删除的重复记录。最小 `Id` 找不到同一 `Email` 下更小的行，所以会留下。写删除前我会先用同样的连接条件 `SELECT` 预览，避免把整组都删掉。

# 1 分钟回答

第一，确认题目假设：`Id` 是唯一主键，`Email` 相同的记录按 `Id` 升序只留第一条。第二，给出可执行写法：`DELETE p1 FROM Person p1 JOIN Person p2 ON p1.Email = p2.Email AND p1.Id > p2.Id;`，`>` 保证每组保留最小 `Id`，不能换成 `<>`。第三，补边界与落地：等值自连接不会匹配 NULL，若 `Email` 可为 NULL，要先约定 NULL 是否属于同一组，改用按 `Email` 分区的窗口函数或 NULL-safe 比较；在支持事务的引擎里先预览待删集合、执行后按 `Email` 分组检查 `COUNT(*)`，并确认 `Email` 上的索引与执行计划没有让连接代价失控。

# 追问

- 为什么连接条件用 `Id > Id`？回答要点：它固定留下每组最小 `Id`；用 `<>` 会让同组记录互相配对，可能把整组删掉。
- `Email` 允许 NULL 时怎么办？回答要点：普通等号不会把两个 NULL 配成一对，应先确认业务口径，再用窗口函数按 `Email` 分区或支持 NULL-safe 的比较实现。
- 删除前怎样降低误操作风险？回答要点：把同一连接条件先用于 `SELECT` 预览，必要时在事务中执行；完成后按 `Email` 分组核对剩余行数和最小 `Id`。
