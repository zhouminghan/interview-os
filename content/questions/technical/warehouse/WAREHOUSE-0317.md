# 六、ID + 更新时间去重（高频）

这个最好答得口语化。

### 方法一：row\_number（推荐）

SQL

```
select *from (    select *,           row_number() over(partition by id order by update_time desc) rn    from t1) awhere rn=1;
```

面试时不要直接背 SQL。

回答：

> 如果需要根据 ID 去重，并保留最新的一条数据，我一般会使用窗口函数。
>
> 先按照 ID 分组，再按照更新时间倒序排序。
>
> 然后通过 row\_number 给每条记录编号，最后取编号为 1 的数据，这样就能保留每个 ID 最新的一条记录。
>
> 这种方式在 Hive 和 Spark SQL 里面都比较常用。

如果继续问大数据量优化：

> 如果数据量比较大，我会关注数据倾斜问题，必要时结合分桶或者 AQE 优化执行效率。

### 一、维度建模

#### 问题1：什么是业务总线矩阵？

回答：

> 业务总线矩阵是用来规划维度和业务过程之间关系的工具。
> 
> 行表示业务过程，例如下单、支付、退款。
> 
> 列表示公共维度，例如时间、用户、商品、渠道。
> 
> 通过业务总线矩阵可以识别哪些维度能够共享，从而避免重复建设，保证指标一致性。

最好举例：

```
          时间  用户  商品  渠道
下单       √   √   √   √
支付       √   √   √   √
退款       √   √   √
```

这样面试官会认为你真学过建模。

* * *

#### 问题2：为什么采用维度建模？

回答：

> OLAP 场景更多关注分析效率和扩展能力。
> 
> 维度建模能够降低 Join 复杂度，便于业务理解，同时支持指标扩展和主题分析，所以我们数仓主要采用维度建模。

追问：

为什么不用三范式？

回答：

> 三范式更适合 OLTP，强调消除冗余和事务一致性。
> 
> 数仓分析场景更关注查询性能和易理解性，所以采用维度建模。

### 二、缓慢变化维（SCD）

这是很多面试官喜欢补刀的问题。

#### 用户等级变化怎么办？

回答：

> 对于变化不频繁的维度，一般采用拉链表管理历史版本。
> 
> 通过 start_time、end_time 记录生效区间。
> 
> 查询某个时间点的数据时，可以还原历史状态。

如果不做拉链表：

> 对于不关心历史状态的字段，直接覆盖即可。

### 三、事实表有哪些？

问题：

> 事实表有哪些类型？

回答：

#### 事务事实表

记录每一次事件。

例如：

订单、点击、播放。

#### 周期快照事实表

记录某个时间点状态。

例如：

每日库存。

#### 累积快照事实表

记录整个生命周期。

例如：

订单创建时间、支付时间、完成时间。

这个问题经常问。

### 四、维度退化为什么要做？

你提到维度退化，这个很加分。

问题：

> 什么情况下会进行维度退化？

回答：

> 对于基数高、变化少、查询频繁的字段，例如订单号、频道ID、视频ID等，我们会直接放到事实表中，不单独拆维表。
> 
> 这样可以减少 Join，提高查询效率。

很多人只知道维度建模，不知道维度退化。

知道这个，会显得做过大数据。

### 五、一致性维度

问题：

> 如何保证不同事实表之间指标口径一致？

回答：

> 我们会建立一致性维度，例如时间维度、用户维度、渠道维度。
> 
> 多个事实表共享这些公共维度。
> 
> 这样能够保证跨主题分析时指标口径统一。

这里其实和业务总线矩阵联系起来。

### 六、宽表和星型模型怎么选择？

问题：

> DWS为什么做宽表？

回答：

> DWS层主要是公共指标沉淀，会适当宽表化。
> 
> 这样能够减少下游 Join，提高查询效率。
> 
> 但是宽表不会无限扩张，会按照主题域拆分，避免维护成本过高。

追问：

宽表太宽怎么办？

回答：

> 可以按主题拆分，或者保留星型模型，在查询层进行关联。
