# 回答思路

1. 开口先问业务问题、指标口径、分析粒度和实时性要求，避免一上来列组件。
2. 接着定义事件模型：谁在什么时间做了什么，附带哪些属性，以及用户身份和去重键。
3. 然后讲链路：采集与接入、原始层、明细层、聚合层和查询服务，按 SLA 选择批或流。
4. 最后补质量与治理：迟到/重复数据、口径统一、权限合规、监控与回填。

# 一句话

用户行为分析系统以统一的事件模型为主线，把采集、标准化明细、主题聚合和指标服务连起来，并用质量与治理规则保证口径可信。

# 30 秒回答

我会先问这套系统要回答什么问题，是看留存、转化漏斗，还是实时看活动效果。确定指标和粒度之后再定义事件，比如事件 ID、用户标识、事件时间、事件类型和页面属性。数据从埋点进日志或消息队列，落到原始层保留现场，再清洗成统一的明细，按用户或会话聚合给看板和接口用。整个过程还要处理重复上报、迟到事件和身份合并，否则指标再快也不可信。

# 1 分钟回答

第一，定模型与口径：约定事件字典、必填字段、`event_id` 去重键和账号/设备 ID 的映射规则，同时记录指标定义、时间窗口和统计口径。第二，设计链路：SDK 上报到日志或 Kafka，ODS 保留原始 payload，DWD 做解析、字段标准化和去重，DWS 形成用户日、会话或漏斗主题，ADS 再服务看板与 API；分钟级可用批处理，秒级则用流处理并明确迟到数据窗口。第三，补边界与落地：采集前确认用户授权和敏感字段策略，链路中用 schema 校验、量级波动和空值监控，Sink 配合可重放 Source 做幂等写入；指标定义集中在语义层，历史口径变化要保留版本并提供批流对账和回填入口。

# 追问

- 埋点重复或乱序怎么办？回答要点：用事件 ID/业务幂等键去重，以事件时间而非到达时间计算，并为迟到数据设置窗口、补写或重算规则。
- 设备 ID 和账号 ID 怎么打通？回答要点：维护可追溯的身份映射与生效时间，登录前后的行为按规则归一，并评估合并错误对留存和漏斗的影响。
- 怎么保证看板与明细查询结果一致？回答要点：统一指标定义和时间口径，让聚合与明细来自同一份标准化事件，并做例行总量对账和异常告警。
