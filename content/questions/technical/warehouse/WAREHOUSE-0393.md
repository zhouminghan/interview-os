# 一句话

重复指标治理靠「注册前置 + 口径唯一 + 血缘比对」，把重复拦在开发之前；治理好坏用可量化的复用率、口径一致率、重复率和变更成本来评，不靠感觉。

# 30 秒回答

字节 05-27 社招 6 年面经第 7、8 题连问。这题把「数仓规范设计，如何监督规范实施」（同场第 6 题）串起来了：面试官想听的不是有几份规范文档，而是规范怎么变成系统约束。

# 1 分钟回答

- 重复指标怎么来的：不同需求各自建表、同名不同义/同义不同名、口径微调后另起字段、临时报表转正时没回收、跨团队缺少指标目录
- 事前拦截：指标注册制，新建指标前先查指标字典；命名规范 + 业务域/粒度/度量/时间周期四要素唯一确定一个指标，命名冲突直接卡住
- 口径唯一：定义收敛到语义层/指标中台，ADS/DWS 只引用不重复定义；口径变更走评审并同步失效依赖它的下游
- 事中比对：解析 SQL 与元数据做血缘分析，识别「同口径不同名」「同名不同口径」的疑似重复，定期出清单让 owner 认领合并
- 事后收敛：重复指标标记废弃 → 设迁移期 → 下游切换 → 下线，配套影响面分析和公告，禁止直接删表
- 怎么监督规范落地（配套第 6 题）：把规范写进 CI 卡点（建表校验命名/分区/生命周期、SQL 扫描禁全表扫描）、发布流程强制填元数据、违规计入团队看板，而不是靠评审时人肉提醒
- 治理好坏的评价指标：公共模型复用率（被 3 个以上消费者使用的公共表占比）、口径一致率（跨报表同指标结果一致的比例）、重复指标数/重复率、需求交付时长、模型变更影响面、下游报错与回溯工单数
- 过程指标：元数据完整率（表/字段注释覆盖）、规范卡点拦截数与整改率、废弃表回收数、SLA 达标率
- 结果指标才是终点：需求响应从几天降到几小时、口径争议工单下降、新人上手时间缩短——治理不是把文档写漂亮，是让用数成本真的降下来
- 加分：结合 AI 讲元数据补全、同名异义识别、口径变更影响面自动推导，但要先讲清人工规范与血缘基础，否则 Agent 推理没有可靠输入
