> **要点提纲**：场景题压力测试 | 选业务过程→定粒度→列维度→列事实 | 边讲边出 DDL | 退化维 + SCD2 拉链表 + 一致性维度都要带

> **题型说明**：这是大厂数仓岗高频"现场口述"题。面试官会随便丢一个业务过程（创建帖子 / 下单 / 直播开播 / 加购），让你**当场按 Kimball 四步法走一遍**，边讲边在白板上画出事实表 + 维度表 schema。考点是逻辑链条的完整性 + 对每一步取舍的解释力，不在于背得熟。

🎤 **口语演练版**（以"创建帖子"为例，对镜或对面试官就这么说）：

「好，我以**用户创建帖子**这个业务过程为例，按 Kimball 四步法走一遍，边讲边画 schema。

---

**第一步：选择业务过程（Business Process）**

我选的业务过程是 **"用户在频道里创建一篇帖子"**。

为什么选这个？因为它是一个**原子的、可观测的、有时间戳的业务事件** —— 用户点"发布"按钮的那一刻就是事件触发点，对应一条业务系统的写入。要避开"用户活跃"这种**复合状态**类的伪业务过程，那不是单一动作，是多个事件聚合出来的。

业务过程的三个判断标准：①是不是一个动作？②有没有明确时间戳？③上游有没有原子的事件源？三条都满足才能当业务过程。"创建帖子"显然满足。

---

**第二步：声明粒度（Declare the Grain）**

粒度我选 **"一行 = 一次成功创建的帖子"**，业务主键是 `post_id`。

这一步**最容易翻车**，必须用一句话说死，不留歧义。我的粒度声明是：

> "事实表 `dwd_post_create_di` 的每一行，代表频道内一个用户在某一时刻成功创建的一篇帖子（post_id 唯一）。"

注意三个细节：
1. **"成功"** —— 失败的创建（被风控拦下的、草稿）不进这张表，因为业务问的是"今天发了多少帖子"
2. **粒度选 post_id 不选 user_id** —— 一个用户一天可能发多篇，user_id 粒度会丢失明细，没法回推到单帖维度
3. **不能选"用户每天创建帖子"汇总粒度** —— 那是 DWS 层的事情，DWD 必须保持最细原子粒度

粒度定下来之后，后面所有的维度和事实都得围绕这个粒度对齐。

---

**第三步：确定维度（Identify the Dimensions）**

我从"分析师会想看什么角度"反推，列出**七个维度**：

| 维度 | 维度类型 | 物理形态 | 说明 |
|------|---------|----------|------|
| **时间维度** | 公共维度 | `dim_date`（日期）+ `dim_time`（小时分钟） | 一致性维度，全数仓共用 |
| **用户维度** | 公共维度 | `dim_user` | 拉链表 SCD2，记录用户等级、注册渠道变化 |
| **频道维度** | 业务维度 | `dim_channel` | 拉链表，频道分类、Owner 会变 |
| **帖子类型维度** | 退化维度 | 不建表，直接放事实表 | 图文/视频/纯文，枚举值少不值得独立建 |
| **设备维度** | 业务维度 | `dim_device` | iOS/Android、机型、版本 |
| **来源页维度** | 退化维度 | 直接放事实表 | from_page，比如首页 / 个人主页 |
| **审核状态维度** | 退化维度 | 直接放事实表 | 通过/打回，状态码少 |

讲到这里我会**主动点出三个建模决策**：

1. **退化维度（Degenerate Dimension）** —— 帖子类型、来源页、审核状态这种**值域很小、没有自己描述属性**的维度，没必要单独建一张维表，直接以字符串/枚举值放进事实表。这个手法 80% 的初学者会忘，记得讲到。

2. **一致性维度（Conformed Dimension）** —— `dim_user`、`dim_date` 是全数仓多个事实表共用的，必须由 DIM 层统一维护，不能每个事实表团队各建一份，否则跨域 JOIN 时口径会打架。

3. **缓慢变化维（SCD2）** —— `dim_user` 的等级、`dim_channel` 的分类是会变的。我用拉链表的方式（start_dt / end_dt / is_current），保证回溯历史时能拿到"当时的"用户等级，而不是"今天的"。

---

**第四步：确定事实（Identify the Facts）**

事实是**可加的数值度量**，但创建帖子这个事件本身没什么数值——所以这是个典型的**事件型事实表（无度量事实表 / Factless Fact Table）**。

度量我列三个：

| 字段 | 类型 | 可加性 | 说明 |
|------|------|--------|------|
| `post_cnt` | int | **完全可加** | 恒为 1，方便 SUM；这是 factless 表的标准技巧 |
| `content_length` | int | **完全可加** | 帖子字数，可以按维度 SUM 算总字数 |
| `image_cnt` | int | **完全可加** | 配图数 |

可加性这块我会强调一下：
- **完全可加（Fully Additive）**：跨所有维度都能 SUM，比如帖子数、字数
- **半可加（Semi-Additive）**：跨某些维度能 SUM，跨时间不能，比如"账户余额"
- **不可加（Non-Additive）**：比例、率值，比如"通过率"，只能算不能加

创建帖子事实表里都是完全可加，最干净。

---

**最后给出完整 DDL 草图**（边讲边在白板上画）：

```sql
-- 事实表（DWD 层）
CREATE TABLE dwd_post_create_di (
  -- 主键 + 业务标识
  post_id           BIGINT,           -- 业务主键（粒度承载）
  
  -- 维度外键（FK to DIM）
  user_id           BIGINT,           -- → dim_user
  channel_id        BIGINT,           -- → dim_channel
  device_id         STRING,           -- → dim_device
  create_date       STRING,           -- → dim_date（yyyy-MM-dd）
  create_hour       INT,              -- → dim_time
  
  -- 退化维度（直接落表，不独立建维）
  post_type         STRING,           -- 'text'/'image'/'video'
  from_page         STRING,           -- 'home'/'profile'/'channel_detail'
  audit_status      STRING,           -- 'pass'/'reject'
  
  -- 度量（完全可加）
  post_cnt          INT,              -- 恒为 1
  content_length    INT,
  image_cnt         INT,
  
  -- 事件时间戳
  create_ts         TIMESTAMP
)
PARTITIONED BY (dt STRING)            -- 按天分区
STORED AS PARQUET;

-- 用户维度（DIM 层，拉链表 SCD2）
CREATE TABLE dim_user (
  user_id           BIGINT,
  nickname          STRING,
  user_level        INT,              -- 会变
  register_channel  STRING,
  start_dt          STRING,           -- 拉链生效日
  end_dt            STRING,           -- '9999-12-31' 表示当前
  is_current        TINYINT
)
STORED AS PARQUET;
```

---

**收尾**：这就是按四步法落地的全过程。**关键检查点**有四个：

1. 业务过程是不是原子事件？✅ 创建帖子是
2. 粒度有没有用一句话说死？✅ "一行 = 一篇成功创建的帖子"
3. 退化维 / 一致性维 / SCD2 这三个手法有没有用？✅ 都用上了
4. 度量的可加性有没有标清楚？✅ 都是完全可加

如果面试官追问，我可以展开讲：①如何处理"撤回的帖子"（事件型事实表的逆向事件）；②怎么和"帖子互动"事实表做 JOIN（通过 post_id 关联）；③如果业务变了要加"话题维度"该怎么演进（在 DIM 层加新维表，事实表加 FK 列，不影响存量）。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **场景题的核心评分标准是"思维链条完整性"，不是答案对错** —— 面试官想看你是不是能把"业务诉求 → 粒度选择 → 维度抽取 → 事实定义 → 物理 schema"这条链路串通。中间任何一个跳跃（比如直接给 DDL 不解释粒度选择）都会被扣分
>
> - **退化维度 / 一致性维度 / 缓慢变化维这三个名词必须主动讲出来** —— 这是判断 P5 vs P7 的分水岭。P5 的人会说"帖子类型直接放事实表"，P7 会说"这是退化维度的标准处理"——同一个动作，体系化语言决定了你被打到哪一档
>
> - **factless fact table（无度量事实表）** —— 创建帖子、登录、点击曝光这种事件型场景，常常没有自然的数值度量。**标准技巧是加一列恒为 1 的 cnt 字段**让 SUM 能用，同时保留事件时间戳支持时序分析。这个细节面试讲出来加分
>
> - **粒度声明的"一句话原则"** —— 任何粒度都应该能用 "一行 = ..." 的形式说清楚。如果你说不清，就是没想明白。生产中我们会把这句话写在表的 DDL 注释里，作为 schema review 的卡点
>
> - **现场建模题被追问的高频方向（提前准备）**：
>   1. "粒度怎么定的？为什么不是 user 维度？" —— 答：丢失明细，不可逆
>   2. "为什么不直接做宽表 OBT？" —— 答：维度变化频繁时星型更易演进；宽表适合查询稳定的下游聚合
>   3. "怎么处理用户改昵称这种 SCD？" —— 答：拉链表 SCD2，分析时 JOIN ON post_create_dt BETWEEN dim_user.start_dt AND end_dt
>   4. "如果创建帖子有失败/重试怎么办？" —— 答：粒度声明里就限定"成功"，失败走单独的 dwd_post_create_fail_di 表，不混
>
> - **替换业务过程的演练**：把这套四步法套到下面这些场景练熟，应付面试足够了：
>   - 电商：用户下单 / 加购 / 评价 / 退货
>   - 短视频：发布视频 / 点赞 / 关注 / 完播
>   - 直播：开播 / 进房 / 送礼 / 关播
>   - 出行：发单 / 接单 / 取消 / 完成
