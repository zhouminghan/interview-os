> **来源面经**：字节-基础数据部5年数开三面-20260530 Q21

**触发条件**：上游数据源修了 / 清洗逻辑变更 / 业务口径变更 / 历史数据补齐

**完整流程 6 步**：

**① 影响评估（血缘）**——AI Skill 自动做这步：
- 输入目标表 → AI 通过 MCP 解析血缘 → 输出全量上游依赖
- 评估影响范围：影响多少张表、多少下游报表/接口
- 评估时间成本：链路深度 × 单层处理时间

**② 制定回溯方案**：
- **重跑顺序**：从最上游开始，按依赖顺序逐层重跑（**不能跳层**，否则下游用旧数据）
- **时间范围**：按需要回溯的日期范围切片，比如最近 30 天 → 拆 30 个分区独立重跑
- **资源预留**：评估占多少计算资源，避免和正常调度抢

**③ 幂等保障**——必须保证重跑安全：
- INSERT OVERWRITE PARTITION 覆盖式写入，不追加
- 中间表落快照，重跑前备份关键节点便于回滚
- 业务主键去重，防止重复

**④ 执行回溯**：
- 高优队列跑，错峰避开核心调度窗口
- 分批重跑，每批跑完校验数据再跑下一批
- 监控告警全开，异常立刻停跑

**⑤ 校验和切流**：
- 重跑完后对比新老数据差异
- 差异符合预期才切下游报表/接口
- 留备份分区一段时间，万一有问题能回滚

**⑥ 复盘**：
- 把这次回溯的检测点固化进数据质量监控
- 评估是否要建数据集版本管理 + 灰度发布机制

**AI Skill 实战**（项目三）：把上面 ①②④ 三步自动化——AI 接收目标表 → 通过 MCP 解析全量上游依赖 → 批量查每张上游表对应日期分区是否就绪 → 输出"缺失分区清单 + 回溯顺序建议" → DE 确认后通过 MCP 批量发起回溯任务。**原来人工至少半小时的事，现在分钟级出方案，排查遗漏率显著下降**。

---

> 💡 **专家补充**（大数据架构师视角）
>
> - **数据回溯是"DE 日常最高频体力活之一"**——AI Skill 把这块自动化，是 DE 角色从"执行者"转向"方案审核者"的关键场景，价值最高
> - **"不能跳层重跑"是铁律**——新人最容易犯的错就是只重跑出问题的那一层，结果下游用了旧的中间数据。正确做法永远是从最上游开始
> - **数据回溯一定要配版本管理**——回溯前留快照，万一回溯出问题能秒级回滚。"破坏性回溯"是事故的常见源头
