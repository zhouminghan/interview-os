> **来源面经**：字节-基础数据部5年数开三面-20260530 Q33

我说**完整 SOP** 四个阶段：

**第一阶段：应急止血（30 分钟内）**

- **评估影响范围**：哪些任务失败？影响哪些下游？业务方什么时候上班？必须几点前恢复？P0/P1？
- **立刻通知**：钉钉/电话通知影响的业务方负责人 + 直属 leader，**不要等修好了才说**——业务方提前知道才能调整自己的节奏
- **快速止血方案**：
  - 优先级 1：切回稳定版本（逻辑变更导致的就回滚）
  - 优先级 2：扩容/调度提优（资源不足）
  - 优先级 3：数据兜底（短期修不好用昨天数据兜底，标注"数据延迟"）

**第二阶段：根因定位（1~2 小时）**

应急止血完恢复了业务，再来挖根因。**严禁先定位再止血**——业务等不起。

排查链路：
1. 看告警日志——任务失败的报错信息
2. 看 Spark UI / Flink Web UI——OOM、Shuffle 拉取失败、网络异常，还是逻辑错误？
3. 看输入数据——上游分区是否就绪？数据量是否异常？Schema 是否变更？
4. 看资源水位——集群 CPU/内存/磁盘/网络是否打满？
5. 看变更——最近有什么变更上线？回退能否解决？

**典型根因**（按出现频率）：
1. 上游数据异常（最高频）：埋点 bug、上游分区缺失、Schema 变更
2. 数据倾斜：业务高峰期 + 热点 key 集中
3. 资源不足：和其他大任务抢资源，凌晨高峰冲突
4. 逻辑变更：新版本 SQL 没充分测试就上线
5. 集群故障：HDFS 抖动、YARN 资源管理器异常

**第三阶段：彻底解决（半天~2 天）**

- **根因消除**：根据定位结果修代码 / 调资源 / 协调上游 / 优化逻辑
- **验证**：sample 数据小批量验证 → 全量验证 → 对比新老结果差异
- **切流**：差异符合预期才切下游，留备份分区一段时间
- **数据回溯**：如果有错误数据已经流到下游，按数据回溯流程补数

**第四阶段：复盘（事后 1 周内）**

- **时间线还原**：从问题发生到完全恢复，每个时间点谁做了什么
- **根因 5 Why 分析**：表面原因 → 真正根因，挖到组织/流程/工具层面
- **影响评估量化**：影响多少业务方、多少接口失败、多少经济损失
- **整改方案**：
  - 监控固化：把检测点加进数据质量监控
  - 预案补强：补充这种场景的应急预案
  - 流程优化：上线流程是否要加 review？资源配置是否要预留 buffer？
  - 工具升级：AI Skill 数据回溯就是从这种事故里沉淀出来的
- **复盘文档归档**：所有事故复盘进知识库，新人入职必读

**核心原则**：**应急止血和根因定位必须分开**——先恢复业务再挖根因，反过来就是事故扩大。

---

> 💡 **专家补充**（大数据架构师视角）
>
> - **"故障应急 SOP" 是资深 DE 和初级 DE 的分水岭**——初级 DE 慌乱中会想着先挖根因，资深 DE 第一反应永远是"先止血再说"
> - **"凌晨高峰"是离线数仓的特殊性**——凌晨 0~8 点是 T+1 任务的高峰期，告警密集是常态。和互联网业务的"凌晨低峰"完全相反，新人容易认知错位
> - **"复盘文档归档"被低估**——很多团队复盘开完就完了，没沉淀。资深团队会把每次复盘进知识库强制新人必读，避免重复踩坑。这是组织级别的能力沉淀
