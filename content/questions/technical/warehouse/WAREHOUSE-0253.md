# 回答思路

1. 开口先按目标区分：范式建模服务写入一致性，维度建模服务分析查询和业务理解。
2. 接着讲结构差别：范式建模拆表消除冗余，维度建模围绕事实表和维度表组织。
3. 然后给选型：交易系统/源数据模型用范式，BI 与指标层用星型或雪花维度模型。
4. 最后补边界：维度建模也要有统一维度和明确粒度，不能把反规范化当成随意冗余。

# 一句话

范式建模用拆分和约束减少冗余、保证事务一致性；维度建模围绕事实与维度组织数据、降低分析查询的理解与连接成本。

# 30 秒回答

我会先用一句话分场景。范式建模把实体拆到符合 3NF 的表中，更新一处就生效，适合交易系统和需要控制冗余的源模型。维度建模允许在维度表里保留一些冗余，用事实表加维度表组成星型结构，让业务人员容易按时间、地区、商品去切片。落到数仓里，通常是源系统贴近范式，面向分析的 DWD/DWS/ADS 再转成一致的维度模型。

# 1 分钟回答

第一，讲设计目标：范式建模把写入异常和重复存储降到较低水平，表多、JOIN 多；维度建模先声明事实表粒度，再把描述性属性放进维度表，查询路径短、口径容易解释。第二，讲怎么选：高频行级写入和强一致约束在 OLTP 侧用范式，固定主题的历史分析、报表和多维聚合用维度模型；ODS 往往保留源系统形态，不必强行重建成星型。第三，补边界和落地：维度模型依赖一致维度、代理键和缓慢变化维策略，处理历史属性变化；反规范化会增加存储与 ETL 维护成本，也不能用宽表替代业务定义和指标口径治理。

# 追问

- 事实表的粒度为什么最关键？回答要点：一行事实代表一次业务事件还是一个周期汇总，决定可挂哪些维度和度量，粒度含混会导致聚合重复或无法下钻。
- 维度历史变化怎么处理？回答要点：用缓慢变化维保留版本，Type 1 覆盖旧值，Type 2 新增带有效期的版本行，让历史事实能关联当时有效的属性。
- 维度建模一定比范式建模快吗？回答要点：它通常减少 JOIN 并更易表达分析口径，但性能还取决于分区、统计信息和执行引擎，不能把冗余本身当作性能保证。
