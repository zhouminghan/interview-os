# 回答思路

1. 开口先说倾斜是分布问题，先定位再改 SQL，不能一上来加资源。
2. 接着查证据：看各 Stage 的 task 输入量、Shuffle read、耗时和热点 key/NULL 的频次。
3. 然后按成因选方案：过滤无效值、拆分热点、两阶段聚合、广播小表或开启引擎的 skew join。
4. 最后补代价和验证：加盐要还原语义，广播受内存限制，改完要比较长尾 task 和资源用量。

# 一句话

处理数据倾斜先找出少数 task 承接了过多数据的 key 或分区，再按成因做过滤、拆热点、两阶段聚合或 Join 改写，最后验证长尾是否消失。

# 30 秒回答

我会先说不是所有慢任务都叫倾斜，要先看数据分布。比如某个 Stage 绝大多数 task 很快结束，只有一两个 task 的 Shuffle read 特别大，就去查 Join key 或 Group by key 的频次，尤其别漏掉 NULL 和默认值。确认热点后再决定动作：无效 key 先过滤，热点 key 单独拆开，聚合可以加盐做两阶段，小表关联可以广播。改完还要看长尾和总资源，而不是只看参数调大了没有。

# 1 分钟回答

第一，定位：对照执行计划、各 task 的输入/Shuffle 指标和持续时间，按 key 统计 Top N，区分真正热点、空值集中、分区过小或下游写入慢。第二，按场景处理：无业务意义的 NULL 单独过滤，Join 一侧足够小可广播，热点聚合先给 key 加随机前缀局部聚合再去掉前缀全局合并，大表关联可用加盐、拆分热点子集或 Spark AQE skew join。第三，补边界与落地：单纯提高并行度拆不开同一个热点 key；加盐会改变中间 key，必须按业务指标还原结果，广播还要评估 executor 内存。改完后比较最大 task 用时、Shuffle 读写、spill 和结果总量，确认没有把长尾转移到另一个 Stage。

# 追问

- 怎么区分倾斜和整体资源不足？回答要点：倾斜表现为少数 task 输入或耗时远高于同 Stage 其他 task；若大多数 task 都慢，更应查数据量、并行度、I/O 和下游吞吐。
- NULL 或默认值为什么会成为热点？回答要点：大量缺失值都落到同一个分组或 Join key，会让单分区承载过多数据；先判断能否过滤，不能直接丢弃时单独处理。
- 为什么加盐能缓解聚合倾斜？回答要点：随机前缀把同一热点 key 暂存到多个 task 做局部聚合，再去前缀合并，代价是多一轮 Shuffle 且必须保证度量可合并。
