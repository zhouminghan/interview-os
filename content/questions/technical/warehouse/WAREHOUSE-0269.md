# 回答思路

1. 开口先把「实时」换成可验收的 SLA：是秒级可见、分钟级刷新，还是只要求当日更新。
2. 接着确认数据特性：Source 能否重放、是否有更新/删除、迟到多久、维度是否会变。
3. 然后讲分层链路：接入日志、流式明细、主题聚合和面向查询的服务层，批处理保留对账与回填。
4. 最后补一致性：checkpoint、幂等/事务 Sink、主键 upsert、watermark 和监控共同决定结果是否可信。

# 一句话

实时数仓不是把离线调度改短，而是用可重放流、有状态计算、主键更新和服务层把低延迟、可恢复、可对账三件事一起设计。

# 30 秒回答

我会先问业务能接受多久看到数据，以及结果要不要随迟到事件修正。确定 SLA 后，Source 一般从业务日志或 CDC 进 Kafka，流处理做清洗、维表关联和窗口聚合，再写到支持主键 upsert 的湖仓或 OLAP 表供查询。仅有流计算还不够，checkpoint、幂等写入和批流对账决定故障后能不能恢复；离线链路仍要保留，用来回填和校验口径。

# 1 分钟回答

第一，定输入和语义：确认日志/CDC 是否可重放，结果以事件时间还是处理时间为准，更新和删除是否要用 changelog，允许的迟到范围是多少。第二，设计链路：ODS 保留原始流，DWD 做标准化和去重，DWS 按主题维护状态与增量聚合，服务层用支持主键更新、点查和聚合的引擎承接看板/API；维度变化要带版本，避免用最新维表覆盖历史事实。第三，补边界和落地：可重放 Source、checkpoint 与幂等或事务 Sink 组合才能控制重复写入，watermark 触发窗口后还要有迟到修正和重算入口；用延迟、吞吐、失败回放、批流差额监控 SLA，并明确实时结果在故障恢复期间是最终一致而非永久瞬时一致。

# 追问

- 迟到事件怎么处理？回答要点：用 watermark 决定正常窗口何时输出，再设置允许迟到、侧输出或撤回/更新路径，超过窗口的数据走补写或离线重算。
- 维表更新后历史结果要不要变？回答要点：按业务口径选择事实发生时的维度版本或当前维度；需要历史可复现时应存带有效期的维表快照。
- 怎么验证实时与离线结果一致？回答要点：用同一份标准化明细和指标定义做按时间分区的总量与主键对账，保留可重放和回填能力，并监控差异而不是只监控任务是否存活。
