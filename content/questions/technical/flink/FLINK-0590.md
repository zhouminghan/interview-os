> **要点提纲**：有界vs无界 | 增量vs整体 | API 统一 | 触发时机 | 容错差异 | Iceberg 桥梁
> **来源面经**：美团-数据开发实习一面-20260430 Q5

核心区别是**数据是否有界（bounded）**。

**流数据**：无界，数据持续到达，永远不知道下一条什么时候来。计算是**增量**的——靠 watermark 推进事件时间、窗口划分计算单元、state 累积中间结果。

**批数据**：有界，数据集大小已知，可以**整体计算**完输出。

**Flink 流批一体能力**：同一套 DataStream API 既能处理无界流也能处理有界批（设置 execution mode 为 BATCH），SQL 层面也是同一套语法。

**具体差异**：

| 维度 | 流处理 | 批处理 |
|---|---|---|
| 触发时机 | 来一条算一条 / 窗口到点触发 | 数据全到齐一次算 |
| 容错机制 | checkpoint 持续做快照 | 失败重跑整个 stage |
| Shuffle | 必须 pipeline 流式传输 | 可 blocking shuffle 落盘 |
| 资源使用 | 长期占用 | 跑完释放 |
| 时间语义 | 强调事件时间 + watermark | 处理时间为主 |

**流批一体落地实践**：**Flink 处理 Kafka 流写 Iceberg，Iceberg 这层就是流批桥梁**——Flink 实时写、Spark 批量读，本质上是流批一体的实际形态。

> 💡 **专家补充**：
> - **流批一体的真正难点是"统一存储"而非"统一计算"**——Flink 早就支持流批两种执行模式了，但没有 Iceberg/Hudi 这种 ACID 表格式，存储层不统一就只能在计算层"流批一体"，数据还是分两份
> - **批是流的特例**——这是 Flink 设计哲学的核心，无界流加上"读到数据末尾就停"就退化成有界批。从这个视角看，流处理引擎跑批是降维使用，反过来批引擎跑流就很别扭
> - **Lambda 架构正在被流批一体逐步替代**——以前需要离线+实时两套代码两套链路，未来一套 Flink + 一套 Iceberg/Hudi 就能搞定，开发和维护成本大幅降低
