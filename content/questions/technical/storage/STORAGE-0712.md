# 回答思路

1. 开口先加版本限定：这里讨论的是旧版 Hive 的 `CREATE INDEX`，Hive 3.0 起已移除该机制。
2. 接着讲直接成本：索引本身要另存一份数据，还要扫描基表、按索引列排序并生成映射，占用存储和计算资源。
3. 然后讲持续成本：基表写入或分区变更后索引可能过期，需要重建或同步，查询优化器也未必总能命中。
4. 最后给现代表达：分区裁剪、分桶、列式文件的统计信息与 predicate pushdown 通常是更常见的替代。

# 一句话

旧版 Hive 索引的成本包括额外存储、构建时扫描排序、数据变更后的维护，以及优化器不一定命中的机会成本；现代 Hive 更常用分区和列式文件裁剪。

# 30 秒回答

我会先说这是旧版 Hive 的能力。建索引不是只多一个元数据标记，Hive 会生成一张索引表，扫描基表并按索引列组织键值和文件位置，所以要付存储和构建计算的代价。之后数据变了还要重建或同步，查询也未必一定走索引。现在更常见的是用分区裁剪、分桶，以及 ORC/Parquet 的统计信息和谓词下推来减少扫描。

# 1 分钟回答

第一，讲一次性成本：`CREATE INDEX` 会创建额外的索引表，构建时要读取基表、排序/组织索引列并保存指向原数据块的信息，带来存储、CPU 和作业时间。第二，讲持续成本：基表新增分区、重写文件或更新数据后，索引与数据可能不一致，需要 `REBUILD` 或调度同步；写入链路因此变长，查询优化器也只有在代价合适且谓词匹配时才使用它。第三，讲版本和落地边界：Hive 3.0 起移除了旧索引机制，且低选择性谓词即使有索引也可能不如全表扫描；实际优化应优先检查分区、文件布局、列式统计和 Bloom filter 等是否能减少读取量。

# 追问

- Hive 索引里存的是什么？回答要点：旧实现会另建索引表，保存被索引列的值与对应文件/块位置，以便查询时缩小扫描范围，因此额外占用存储。
- 基表数据变化后为什么还要维护？回答要点：索引指向的是构建时的数据位置，新增或重写文件后可能过期，需要重建或同步，否则可能漏读或得不到收益。
- 为什么建了索引查询仍不快？回答要点：谓词选择性低、优化器未选用索引或列式文件已经能跳过大量数据时，索引收益有限；Hive 3.0 起应转用分区裁剪与文件级统计等机制。
