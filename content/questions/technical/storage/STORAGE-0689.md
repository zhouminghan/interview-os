# 回答思路

1. 开口先澄清：Schema on Read 不是「没有 schema」，而是表结构保存在 metastore，文件写入时不逐行校验。
2. 接着讲查询过程：引擎读文件时才按字段定义、SerDe 和分隔符把字节解释成行。
3. 然后对比关系库：Schema on Write 在写入时检查类型和约束，Hive 更适合先落地多样数据。
4. 最后补代价：结构不兼容要在读取或入仓质量校验中暴露，不能把灵活性当成数据质量保障。

# 一句话

Schema on Read 指数据写入文件时不强制逐行校验结构，查询时才按 metastore 中的表 schema 和 SerDe 解释数据。

# 30 秒回答

我会先说这不是没有表结构。Hive 建表时已经定义了字段，但底层文件可以先落到 HDFS 或对象存储，写入阶段不会像关系库那样逐行检查每个值。等到查询时，引擎才按表字段、分隔符和 SerDe 把文件解析成记录。这样接入异构数据更灵活，代价是脏数据往往到读取或入仓校验时才暴露。

# 1 分钟回答

第一，讲清结构在哪里：列定义和位置等元数据在 metastore，文件内容在外部存储，二者是解耦的。第二，讲读取行为：缺列通常补 NULL，多余列按当前 schema 忽略，类型无法解析时可能得到 NULL 或直接报错，具体取决于 SerDe、文件格式和执行引擎。第三，补边界和落地：变更表 schema 主要影响之后的解析，历史文件未必自动变合法，所以 ODS 接入后仍要做字段数量、类型、空值和行数校验；需要强约束、低延迟写入校验的场景更适合 Schema on Write 的存储。

# 追问

- Hive 既然是 Schema on Read，为什么建表还要写字段？回答要点：字段定义是读取时解释文件的依据，放在 metastore 中，写入文件本身并不携带或强制执行这套结构。
- 文件与表结构不匹配会怎样？回答要点：缺列、额外列和类型转换的表现取决于 SerDe 与引擎，可能是 NULL、忽略或报错，因此需要显式的数据质量校验。
- 它和关系库的 Schema on Write 怎么选？回答要点：前者便于快速接入和演进原始文件，后者在写入时保证约束；分析型湖仓通常先用前者落原始数据，再在入仓层强化校验。
