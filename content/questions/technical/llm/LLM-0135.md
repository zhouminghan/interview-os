> **来源面经**：阿里系-AI数据工程师两面-20260521 集团2-Q7.5

LLM 的不确定性是天生的，原因可以拆成 **5 个层面**：

**1. LLM 本身的随机性**

- **采样温度（temperature）**：>0 时输出不确定，温度越高越发散
- **Top-K / Top-P 采样**：从概率最高的 K 个 token 里随机选
- **解决**：生产环境用 `temperature=0` + `seed` 固定，但仍不能完全消除（API 内部还有随机性）

**2. 上下文召回的不稳定**

- **RAG 召回**：向量召回的 Top-K 文档可能因为相似度边界附近的小波动而变化
- **不同的召回内容 → 不同的 Prompt → 不同的输出**
- **解决**：用 reranker 二次精排 + 召回结果缓存

**3. 上下文窗口溢出**

- 长对话或大知识库时 token 超出，**不同截断策略导致不同结果**
- **解决**：上下文压缩 + 摘要 + 滑动窗口

**4. 工具调用的副作用**

- AI 调用 MCP 工具（如查实时元数据）每次返回内容可能变化（数据有更新）
- **解决**：关键工具加缓存层，幂等性强的工具复用结果

**5. 多步推理的累积误差**

- 多步 Agent 任务（如 ReAct）每一步都有不确定性，**长链路误差累积**
- 第 1 步错了后面全错
- **解决**：缩短链路 + 每步加校验 + 失败重试

**生产环境的应对策略**：

| 措施 | 效果 |
|------|------|
| `temperature=0` + 固定 seed | 减少 80% 不确定性 |
| RAG 召回结果缓存 | 同样问题召回稳定 |
| 关键步骤加幂等校验 | 跨次执行结果一致 |
| 输出 JSON Schema 强约束 | 结构化字段不会漂移 |
| Self-Consistency（多次采样取一致） | 适合容忍延迟的场景 |
| 用户反馈闭环 | 长期看准确率持续提升 |

**项目里的真实例子**：我们的 Skill 默认走 `temperature=0`，但**对外部 API 的依赖**（比如查实时分区状态）会让结果有变化——同样的"我要回溯 user 表"，今天上游分区都齐 / 明天有缺失，输出的回溯计划就不同。这种是**业务层的合理变化**，不是 Bug。

**回答模板**：「5 个层面原因——**LLM 采样温度**、**RAG 召回不稳定**、**上下文窗口溢出**、**工具调用副作用**、**多步推理累积误差**。生产应对靠 `temperature=0` + 召回缓存 + Schema 约束 + 反馈闭环。但要区分**真不确定（要消除）**和**业务层合理变化（不应消除）**——比如 AI 查实时分区状态，今天和明天结果不同是正常的。」

> 💡 **专家补充**（AI 工程师视角，面试中视情况展开）
>
> - **「LLM 不确定性」在 2024 年之后被严重放大**——业务方期望"AI 应该和报表一样稳定"，但 LLM 本质上有随机性。这种**期望管理**比技术解决更重要，要主动告知业务方"Agent 问数适合探索，关键决策走稳定报表"
> - **`temperature=0` 不是银弹**——OpenAI 的 GPT-4 即便 temperature=0 也不完全确定（API 内部并行计算的浮点数误差），Anthropic 的 Claude 相对更稳定。生产选型要测试
> - **Self-Consistency（多次采样取一致结果）是近年学术界的热点方法**——同一个问题问 5 次取多数答案，准确率显著提升但延迟和成本翻倍。适合**离线批处理**而非实时
> - **回答这题的高分姿势是「区分真不确定和业务变化」**——很多候选人只讲消除随机性，但生产环境**业务变化导致的结果不同是合理的**。能讲清这个区分，立刻显示出**真做过 Agent 工程**
