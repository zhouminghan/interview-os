> **来源面经**：阿里系-AI数据工程师两面-20260521 集团2-Q7.1

这道题考察的是 **「表元数据治理 → AI 可消费 → 人也好读」** 的完整设计。我按 **5 类信息** 来讲。

**1. 基础元数据（机器读为主）**

| 字段 | 说明 |
|------|------|
| 表名（标准命名） | `dwd_user_active_di` 体现层级+主题+粒度 |
| 字段列表 | 字段名、类型、是否可空、注释 |
| 分区字段 | `dt` / `hour`，AI 写 SQL 必须知道 |
| 主键 / 业务键 | 决定 JOIN 和去重逻辑 |
| 表大小 / 行数 | 影响 AI 选择 BroadcastJoin 还是 ShuffleJoin |
| 数据更新频率 | T+1 / 小时级 / 实时 |

**2. 业务语义（人和机器都需要）**

| 字段 | 说明 |
|------|------|
| 表中文名 + 一句话描述 | "QQ 频道用户日活明细表，每行 = 一个用户每天的活跃明细" |
| 业务域 / 主题 | 用户域 / 内容域 / 流量域 |
| 粒度声明 | "一行 = 一个 user_id + 一天" 写死，不留歧义 |
| 字段业务含义 | 不只是字段名注释，要讲清楚口径（"DAU" vs "周活") |
| 关联表 + 关联字段 | "可关联 dim_user.user_id 取用户维度" |

**3. 数据质量（AI 决策可信度的依据）**

| 字段 | 说明 |
|------|------|
| 是否有质量校验 | 主键唯一性、非空、值域 |
| SLA 等级 | S 级（核心）/ A 级（重要）/ B 级（普通） |
| 历史稳定性 | 近 30 天有无失败、是否有补数据 |
| 数据安全分级 | 机密 / 秘密 / 普通（决定脱敏策略） |

**4. 血缘信息（AI 做归因和回溯）**

| 字段 | 说明 |
|------|------|
| 上游依赖 | 这张表由哪些表加工得来 |
| 下游消费 | 这张表被哪些下游使用 |
| 加工逻辑 | SQL 任务 / 调度配置 |

**5. 使用样例（让 AI 学会怎么用）**

| 字段 | 说明 |
|------|------|
| 典型查询示例 SQL | 3~5 个常见查询模式 |
| 常见坑 | "这张表的 user_id 包含游客，要 WHERE user_type='real'" |
| 责任人 + 联系方式 | AI 兜底失败时让人接管 |

**项目里的实际做法**：我们 QQ 频道用 AI Skill 自动给每张核心表生成「**表知识文件**」，覆盖以上 5 类信息——这是 AI 能在我们数仓上准确做事的核心前提。新人来了也能直接看表知识文件而不是问老员工，**人和 AI 共用同一份知识源**。

**回答模板**：「分 5 类信息——**基础元数据**（字段+分区+主键给机器看）、**业务语义**（粒度+口径+关联给人和机器都看）、**数据质量**（SLA+校验给 AI 决策可信度）、**血缘**（上下游给归因）、**使用样例**（典型 SQL+常见坑给 AI 学怎么用）。我们项目用 AI 自动生成「表知识文件」覆盖这 5 类——核心是**人和 AI 共用同一份知识源**。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **「让人和机器都好理解」是治理的核心难题**——传统 wiki 是给人看的（自由格式），传统元数据是给机器看的（结构化但缺业务语义），AI 时代要求**两套合一**——结构化 + 业务语义都要有
> - **「表知识文件」是 2025 年新兴的产物**——把表的全方位信息（元数据 + 业务语义 + 质量 + 血缘 + 样例）沉淀成一个 Markdown 文档，既给新人看又给 AI 用。dbt docs、阿里 OneData 都在这个方向
> - **粒度声明是被严重低估的核心元数据**——能写出 "一行 = 一个 user_id + 一天" 这种粒度声明的表，AI 写 SQL 准确率会大幅提升。粒度模糊的表 AI 几乎没法用
> - **回答这题的高分姿势是「分类 + 项目案例」**——能讲出 5 类信息的同时给项目里的「表知识文件」实战，立刻显示出**做过 AI 数据工程**而不是只看过文章
