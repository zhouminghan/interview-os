> **来源面经**：阿里系-AI数据工程师两面-20260521 集团1-Q5.3

这两者**不是替代关系，是覆盖不同场景的互补关系**。

**核心差异**：

| 维度 | 传统大报表 | Agent 问数 |
|------|----------|-----------|
| **交互方式** | 看报表 + 钻取（结构化） | 自然语言对话 |
| **使用门槛** | 业务方要会看报表 / 会简单 SQL | 任何人会说人话就行 |
| **覆盖场景** | 高频核心指标（事先定义好） | 长尾问题、临时探索 |
| **响应延迟** | 秒级（预计算） | 几秒到几十秒（LLM 推理 + SQL 执行） |
| **答案稳定性** | 确定（同样输入同样输出） | 不确定（LLM 有温度） |
| **维护成本** | 高（每个看板要建模 + 出库） | 中（依赖知识库 + Agent 准确率） |
| **覆盖率** | 低（人能想到的指标才有） | 高（可应对未知问题） |

**用业务场景类比**：

- **大报表 = "套餐菜单"**：精心烹制、固定菜品、出餐快、做不到的菜没有
- **Agent 问数 = "私人厨师"**：你说啥它做啥、灵活但贵、做出来的可能不如套餐稳定

**为什么 Agent 问数是趋势而不是替代**：

1. **传统报表覆盖不了长尾**——80% 的业务问题是非高频的临时问题（"上周华东区周末的客单价分时分布"），建报表不划算
2. **业务方对 BI 工具学习成本高**——Tableau、DataTalk、QuickBI 入门门槛对非数据岗仍然不低，Agent 问数让运营/产品自己取数
3. **数据团队人效瓶颈**——业务方临时取数请求把 DE/DA 时间打成碎片，Agent 问数把 80% 临时取数自动化解决

**两者的协作模式**：
- **大报表服务高频核心指标**（DAU、GMV、留存率），保稳定保性能
- **Agent 问数服务长尾探索性需求**，给覆盖度
- **Agent 问数能力反向倒推大报表升级**——发现某些问题被频繁问就建成报表

**项目里的实践**：我们 QQ 频道有 DataTalk 大报表覆盖核心指标，同时探索 Agent 问数服务运营临时需求。Agent 问数当前准确率还有提升空间，**用作辅助而非完全替代**——业务方先用 Agent 探索，关键决策仍走大报表。

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **「Agent 问数会替代 BI」是 2024 年的伪命题**——业内已经达成共识，两者长期共存。Tableau / Power BI 都在集成 Agent 问数能力，不是被替代而是被增强
> - **Agent 问数的核心瓶颈不是 LLM 而是元数据和语义层**——LLM 已经够强，但数据团队的元数据混乱（字段命名不规范、口径不统一、表关系不清晰）让 Agent 写不出对的 SQL。所以做 Agent 问数本质上是在**逼迫数据团队把元数据治理做扎实**
> - **「Text-to-SQL」准确率天花板大概在 70~85%**（因业务复杂度而异）——剩下的 15~30% 必须靠语义层、知识库、人工审核兜底。号称 95%+ 的厂商通常是在简单数据集上跑的 demo
> - **回答这题最容易翻车的是没有「项目实战感」**——光对比维度面试官能看出是背的，能讲出"我们 DataTalk 怎么用、Agent 问数怎么用、两者怎么协作"立刻显得真做过
