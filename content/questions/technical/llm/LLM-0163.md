数据回溯的触发场景：
- **上游表结构变更**：新增/删除字段影响下游 ETL 逻辑，需要回溯下游表的历史数据
- **口径修正**：发现某个指标的计算逻辑有 bug，修正后需要重刷历史分区
- **新表建设**：新建一张表需要补充历史数据（比如 bitmap 表需要从第一天开始累积）

巡检的检查项：
1. **依赖完整性**：回溯表的所有上游分区是否就绪（比如回溯近 30 天数据，30 个分区的上游表是否全部有数据）
2. **分区连续性**：目标时间范围内是否有缺失分区（有些表可能中间有一天没跑）
3. **字段一致性**：回溯 SQL 引用的字段在历史分区是否存在（可能字段是后来新增的）
4. **资源评估**：估算回溯任务的数据量和计算资源需求，避免一口气提交 100 天的回溯把集群打爆

发现问题后：
- 上游缺数据 → 先触发上游的回溯或标记跳过
- 字段不存在 → 对不同时间段使用不同 SQL（有字段的用新 SQL，没字段的用兼容 SQL 填默认值）
- 资源超限 → 自动拆分成多批次（比如一次回溯 7 天）
