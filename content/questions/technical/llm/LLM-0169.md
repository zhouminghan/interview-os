DI 和 DF 的关联逻辑：

```sql
-- DF表的每日更新逻辑
INSERT OVERWRITE TABLE dws_xxx_bitmap_df PARTITION(imp_date='${today}')
SELECT
    COALESCE(di.channel_id, df.channel_id) AS channel_id,
    COALESCE(di.uin, df.uin) AS uin,
    -- 拼接：今日flag + 昨日bitmap截断到729位
    CONCAT(
        COALESCE(di.active_flag, '0'),
        SUBSTR(COALESCE(df.active_bitmap, REPEAT('0', 730)), 1, 729)
    ) AS active_bitmap
FROM dws_xxx_bitmap_di di  -- 今日DI表
FULL OUTER JOIN dws_xxx_bitmap_df df  -- 昨日DF表
    ON di.channel_id = df.channel_id
    AND di.uin = df.uin
WHERE df.imp_date = '${yesterday}'
```

**DI 表没数据的处理**：

情况一：DI 表分区存在但为空（上游跑了但那天没有用户行为数据）→ FULL OUTER JOIN 中 DI 侧为空，`COALESCE(di.active_flag, '0')` 自动填 '0'，DF 表正常更新，所有用户当天 flag 为 0。

情况二：DI 表分区不存在（上游任务失败没跑出来）→ **不能直接跑 DF**。巡检机制会检测到上游分区缺失，阻塞 DF 的执行。处理方式：
- 等待上游补跑 → DI 分区就绪后自动触发 DF
- 超时处理 → 如果确认当天数据丢失无法恢复，手动创建一个空 DI 分区，让 DF 继续累积（当天所有 flag 为 0）
- 绝不允许跳过某天直接用前天的 DF → 这会导致 bitmap 位偏移，后续所有数据错位
