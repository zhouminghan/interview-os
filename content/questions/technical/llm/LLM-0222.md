# 一句话

别答工具清单，按「哪些环节交给 AI、哪些必须人把关、怎么验证 AI 的产出、怎么把经验沉淀成资产」四层讲，最后给一个自己踩过坑的例子。

# 30 秒回答

快手 10-21 FDE 一面的收尾思考题，字节 05-27 社招 6 年面经第 15 题问的是同一件事（「你日常开发如何通过 AI 赋能提效」）。开放题最容易答成「我用 Cursor 写代码」，那基本就停在第一层了。

# 1 分钟回答

- 第一层 分工：把工作拆成可验证与不可验证两类——样板代码、SQL 草稿、单测、日志归类、文档初稿交给 AI；架构取舍、口径定义、线上变更、权限与安全决策由人负责
- 第二层 把关：AI 产出必须可验证才敢用（SQL 跑 EXPLAIN 和结果对账、代码过单测与静态扫描、结论回查原始文档），把「AI 写的 SQL 你敢上线吗」答成有校验关卡的流水线，而不是「我会 review 一遍」
- 第三层 输入质量：给 AI 的不是一句需求，而是表结构 + 口径说明 + 历史 Bad Case + 团队规范；上下文/知识库不准，模型再强也是稳定地错——这层和数仓元数据治理直接连上
- 第四层 沉淀：把反复有效的用法固化成 Skill / 模板 / SOP / 评测集，让个人技巧变成团队资产，并用一组 case 集做回归，防止改 Prompt 后悄悄退化
- 给具体例子：如「用 AI 生成数据倾斜排查步骤后，把定位流程沉淀成 SOP，但阈值判断保留人工」，要有前后耗时或质量对比，别只讲感受
- 讲边界与代价：幻觉、上下文过期、Token 成本、敏感数据外发、过度依赖导致能力退化；主动说「哪些场景我不用 AI」比一味吹更能取信
- 和岗位对齐：数开岗落到取数、口径核对、数据质量巡检、异常归因；Agent 岗落到工具设计、评测集、Bad Case 闭环。快手 FDE 一面同场就在问知识库更新方式、输入输出、效果，这题其实是在看你会不会自己定义Agent 的验收标准
- 避雷：不说「AI 会取代工程师所以只要会提问」、不列举一堆没用深的工具名、不把 AI 产出当事实直接引用
