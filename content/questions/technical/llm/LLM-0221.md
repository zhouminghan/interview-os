# 一句话

SSE 适合「服务端单向持续推送 token/进度」的场景，比 WebSocket 轻、能走普通 HTTP 与网关；断线或长连接不可用时按明确条件退化为轮询，保证任务状态最终可见。

# 30 秒回答

美团 10-30 二面第 20 题。Agent 平台岗问这题不是考协议细节，是考「长任务执行中前端怎么知道进度、连接断了怎么兜底」。

# 1 分钟回答

- 选型理由：流式 token、工具执行进度、审计任务状态都是服务端→客户端单向流，SSE 基于 HTTP/1.1 即可，无需升级握手，天然兼容代理/网关和鉴权
- 对比 WebSocket：WebSocket 双向、有独立心跳与重连协议，成本高；这里客户端只需要收，双向能力是浪费
- 事件设计：带 event id 与序号，客户端记录 last-event-id，重连时服务端从断点续推，避免重复渲染或漏中间状态
- 心跳保活：定时发注释帧维持连接，心跳间隔要小于网关/负载均衡的空闲超时；超时阈值按「连续丢 N 个心跳」判定，而不是单次网络抖动
- 降级触发条件：连续重连失败达阈值、SSE 连接被网关/代理拒绝或不支持、心跳超时且重试无效、页面被浏览器冻结后恢复、企业网络明确禁用长连接
- 降级策略：改为按任务 ID 定时拉状态接口，轮询间隔做指数退避 + 抖动，服务端状态接口必须能返回完整当前快照而非增量
- 幂等与恢复：无论 SSE 还是轮询，任务状态以服务端持久化为准；审计服务重启时执行到一半的任务按状态机重跑或续跑，前端只做展示不持有真相
- 分层超时：连接层、单次请求层、任务整体层分别设超时，异常分别处理（重连 / 重试 / 标记失败转人工）
