> **来源面经**：阿里系-AI数据工程师两面-20260521 集团1-Q5.5

这是 Agent 问数的**老大难问题**——业务方说"DAU"，可能数仓里叫 `daily_active_user`、`active_uv`、`d_active_cnt`，三张表都有但口径还略不同。解决方案是**「语义层 + 同义词映射 + 指标注册中心」**三件套。

**1. 语义层（Semantic Layer）—— 最核心**

把"业务概念"和"物理字段"解耦——业务方说的"日活"在语义层定义为 `metric: DAU`，语义层负责把 `DAU` 翻译成具体表的 `daily_active_user` 字段。

- 工业界常见实现：dbt Semantic Layer / Cube.js / Looker LookML / 阿里 OneData
- AI 读语义层而不是读原始表元数据，准确率立刻上一个台阶

**2. 同义词词典（Synonym Mapping）**

人工维护一份「业务术语 ↔ 标准字段名」的词典：

```yaml
DAU:
  standard: daily_active_user
  synonyms: [日活, 活跃用户, active_uv, d_active_cnt, 活跃UV]
  table: dws_user_active_da
  formula: COUNT(DISTINCT user_id)
```

Agent 收到提问时先做**同义词归一化**——把"活跃 UV"映射到 `DAU` 标准概念，再去找对应的表和字段。

**3. 指标注册中心（Metric Registry）**

这是数仓治理层面的根治方案——所有对外指标必须在中心注册，登记：
- 标准名称、同义词列表
- 业务定义、口径、计算公式
- 负责人、来源表、更新频率

**新增指标**走审核流程，**变更指标**走影响评估。Agent 问数直接读注册中心，从源头保证字段一致。

**4. 兜底：用户反馈闭环**

Agent 答错时让用户标注（"你说的 DAU 我理解成了 active_user_count，正确的是哪个？"），把反馈反哺到同义词词典，**越用越准**。

**项目里的实战经验**：我在 QQ 频道做指标治理时就踩过这个坑——前期不同团队对"互动率""活跃用户"定义都不一样，跨团队对数对不上。后来推动了：
- 所有对外指标在 OLA 平台**强制注册**（标准名 + 同义词 + 口径 + 负责人）
- 新增指标走审核才能上线
- 推 Agent 问数项目时直接对接 OLA，AI 看到的是治理过的指标而不是裸字段

**回答模板**：「这是 Agent 问数最难的问题之一，根治方案是**语义层 + 同义词词典 + 指标注册中心**三件套——把业务概念和物理字段解耦，AI 读的是治理过的语义层而不是裸表元数据。我在 QQ 频道做指标治理推动了 OLA 平台的强制注册，这套机制对后续 Agent 问数赋能非常关键——**Agent 问数倒逼数据团队把元数据治理做扎实**。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **这道题考察的不是 AI 能力而是数据治理能力**——能把这道题答出"语义层 + 注册中心"的同学，立刻显示出**资深 DE + AI 工程师**的复合视野，比纯 AI 背景的候选人更有优势
> - **「语义层」在 2025 年成了热词**——dbt、Cube.js、阿里 OneData 都在推，本质都是把"业务概念"沉淀成可被 AI 消费的结构化资产。这是 AI 数据工程师必须了解的基础设施
> - **同义词词典看似简单实则难维护**——业务术语会随产品演进而漂移（"活跃用户"在不同产品阶段口径不同），词典维护是个长期治理工作，不是一次性投入
> - **能讲出「这本质是数据治理问题不是 AI 问题」是高分姿势**——很多候选人会试图用 fine-tune LLM 来解决，但生产实践证明治理才是根治方案
