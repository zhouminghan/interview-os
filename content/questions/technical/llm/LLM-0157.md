我们的流程编排更偏 **Plan-and-Execute** 模式，而不是纯 ReAct。原因是数仓开发的任务边界相对清晰——从需求澄清到最终上线是一个确定性很强的有向流程，不需要 Agent 在执行过程中反复 observe-think-act 循环。

但在 **单步 Skill 执行** 内部，用了 ReAct 的思路。比如"建模 SQL 生成"这个 Skill 被激活后：

1. **Thought**：分析用户意图——要建的表是什么粒度、什么分区策略、什么业务过程
2. **Action**：调用知识库检索，拿到相关表的元数据和建模模板
3. **Observation**：拿到的元数据包含表结构、字段口径、分区策略
4. **Thought**：判断应该套用哪个模板（bitmap/di/df 关联/普通宽表）
5. **Action**：渲染模板 + LLM 补充变体逻辑，生成 SQL
6. **Observation**：质检引擎校验结果

整体是 **Plan-and-Execute 做宏观编排，ReAct 做微观步骤内的推理决策**。如果纯用 ReAct 做整个四阶段流程，Token 消耗会爆炸，而且长链条容易跑偏。Plan-and-Execute 的好处是每个阶段有明确的检查点和人工卡口，不会让 Agent 一口气跑完整条链路。
