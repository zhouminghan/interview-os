> **来源面经**：字节跳动-大数据开发实习抖音电商-20260511 Q11

Skill 的本质是 **「被约束的 Prompt 模板 + 工具调用 SOP」**，从工程角度看，一个完整 Skill 由 6 个核心组成部分：

**第一部分：元信息（YAML 头）**
- Skill 名称、描述、版本号；
- **触发关键词列表**——用户消息匹配到这些关键词就自动触发该 Skill（如"回溯""backfill""补数据"触发数据回溯 Skill）；
- 适用场景说明、不适用场景说明（防止误触发）。

**第二部分：执行步骤（Markdown 主体）**
- 分步骤详细描述每一步要做什么，每一步是一个独立的 prompt 片段；
- 比如"第一步：解析用户输入的目标表名 / 第二步：通过 MCP 调血缘工具查上游 / 第三步：批量调分区查询"——每一步明确**输入、操作、输出**。

**第三部分：必加载的上下文（知识库引用）**
- 指定该 Skill 启动时必须读取哪些文件作为上下文：业务知识库、表元数据、规范文档；
- 这是减少 AI 幻觉的关键——没有上下文 AI 自由发挥，有上下文 AI 在规范内生成。

**第四部分：MCP 工具调用顺序**
- 明确该 Skill 会用到哪些 MCP 工具、调用顺序、参数要求；
- Agent 严格按这个顺序调，不让 AI 自由决定调用哪个工具。

**第五部分：输出格式约束**
- 规定输出的最终格式，比如回溯 Skill 输出"缺失分区清单 + 回溯顺序建议"的标准结构；
- 建模 Skill 输出符合团队 DDL 规范的 SQL 骨架。

**第六部分：自检规则（前置卡点）**
- 内置校验规则——命名规范、分区字段必填、负责人字段必填等；
- AI 生成完后自动 check 一遍再返给用户，避免低级错误。

**Skill 文件物理结构示例**：

```yaml
---
name: data-backfill
description: 数据回溯方案生成
triggers: [回溯, backfill, 补数据]
context_files:
  - knowledge/血缘元数据.md
  - knowledge/数仓规范.md
mcp_tools: [lineage_query, partition_check, backfill_task]
---

# 执行步骤
## Step 1: 解析输入
...
## Step 2: 查上游血缘
...
```

**Skill 的核心设计哲学**：把"好的 prompt + 工具调用 + 上下文 + 自检"全部封装在 SOP 里，**不同用户用同一个 Skill 输出质量是稳定的**。这是从"个人提效"走向"团队提效"的关键。

> 💡 **专家补充**：
> - **Skill 框架的本质是"工程化 Prompt"**——单纯写 Prompt 是个人能力，把 Prompt 工程化为可复用、可触发、可校验的配置才是团队级提效。这就像从写脚本到搭建调度平台的演进
> - **"上下文加载 + 自检规则"是 Skill 的两大杀手锏**：上下文解决"AI 不懂业务"的幻觉问题，自检规则解决"AI 偶尔抽风"的稳定性问题。这两个机制是 ad-hoc Prompt 不具备的
> - **MCP 工具的顺序约束是关键**：让 AI 自由决定调哪个工具风险很大（可能漏调或乱调），Skill 把工具调用顺序硬编码进 SOP，AI 只负责填参数，这样既享受了 AI 的灵活性又避免了它的不靠谱
> - **Skill 设计的最佳实践是"小而专"**——单个 Skill 解决一个具体场景（如"建模 SQL""数据回溯"），不要做大一统 Skill。组合多个小 Skill 反而比一个大 Skill 更易维护、更易测试
