# 一句话

日常走事件驱动的增量 upsert 保新鲜度，全量重建只作为模型换版、切分策略变更或对账发现漂移时的兜底，两者靠版本号隔离。

# 30 秒回答

10-16 AI 数据工程师岗面试题（原帖标 87%）。和「索引一致性」是连问，前者讲怎么发现不一致，这题讲刷新链路怎么搭、什么时候值得推倒重来。

# 1 分钟回答

- 链路：变更事件 → 去重/合并队列 → 解析与切分 → 内容哈希比对 → Embedding 批量调用 → 按 chunk_id upsert → 索引生效 → 对账
- 幂等：每个 chunk 带 doc_version + chunk_hash，重复消费同一事件结果一致；失败可重放且不产生重复向量
- 批量与限流：Embedding 按批调用并做速率控制、重试与退避，长文档拆成可独立失败的分片，避免一条坏文档卡住全量
- 增量适用：文档高频小改、要求分钟级新鲜度、语料规模大（全量重算成本不可接受）
- 全量适用：更换 Embedding 模型、切分策略或归一化规则调整、对账发现大面积漂移、首次建库
- 全量的坑：不能原地覆盖，要建新版本索引（蓝绿），灌完做抽样评测再切流，旧索引保留可回滚
- 成本权衡：增量要维护状态与版本，全量要付算力；一般「增量为主 + 定期全量校准」组合最稳
- 验收：抽样问答集回归、召回 Top-K 命中率、刷新延迟 P95、孤儿/缺失 chunk 数四个指标
