> **来源面经**：阿里系-AI数据工程师两面-20260521 集团2-Q10

知识库是 Agent 问数的"教科书"，分 **5 大类内容**：

**1. 业务知识（让 AI 懂业务）**
- 业务域划分 + 业务流程描述
- 核心业务概念（如社区产品的"频道""订阅""互动"）
- 业务规则（"非活跃用户定义为 30 天无登录"）

**2. 数据资产（让 AI 知道有什么数据）**
- 表清单 + 表知识文件
- 字段元数据 + 业务含义
- 表关系图（哪些表能 JOIN）

**3. 指标定义（让 AI 算得对）**
- 指标注册中心：标准名 + 同义词 + 公式 + 口径
- 常用衍生指标（如"7 日留存率"的标准定义）
- 指标依赖关系

**4. 历史问答（让 AI 越用越准）**
- 历史问题 + 对应 SQL + 反馈结果
- 用户认可的"金标准"问答对
- 失败案例 + 失败原因（避免重复犯错）

**5. 操作规范（让 AI 守规矩）**
- 命名规范（表名 / 字段名）
- 建表规范（必备字段 / 分区设计 / 注释要求）
- 查询规范（必须 WHERE 分区 / 禁止全表扫描 / 大表查询样本量限制）
- 安全规范（PII 字段不能直查 / 数据分级权限）

**知识库的物理形态**：
- **结构化部分**：YAML / JSON / 数据库（指标注册、表关系、字段元数据）→ 给 AI 精确消费
- **非结构化部分**：Markdown 文档（业务流程、表知识文件、操作规范）→ 通过 RAG 向量召回
- **半结构化部分**：典型 SQL 样例（自然语言问题 + 标注答案）→ Few-shot 检索

**知识库不是"建一次就完了"，要做 4 件事**：

| 动作 | 说明 |
|------|------|
| **持续同步** | 数仓变更（新增表 / 改字段）自动同步到知识库 |
| **质量校验** | 定期检查知识库内容是否过时（如指标口径变了 KB 没更新） |
| **反馈闭环** | 用户标注 → 反哺到知识库（同义词词典、典型 SQL 样例） |
| **版本管理** | 知识库 Git 化，可追溯变更历史 |

**项目里的实际形态**：我们知识库主要在做：
- **业务知识**：业务域划分、核心概念解释（人工沉淀）
- **数据资产**：用 Skill 自动给每张核心表生成「表知识文件」
- **指标定义**：对接 OLA 指标注册中心
- **操作规范**：建模规范、命名规范、SLA 规范沉淀成 Markdown
- 历史问答和反馈闭环是**当前的薄弱环节**，需要继续投入

**回答模板**：「5 大类——**业务知识**（业务域 / 流程 / 规则）、**数据资产**（表清单 + 表知识文件 + 关系图）、**指标定义**（注册中心 + 同义词）、**历史问答**（金标准 + 失败案例）、**操作规范**（命名 / 建表 / 查询 / 安全）。物理形态分**结构化（指标 / 关系）+ 非结构化（业务文档）+ 半结构化（典型 SQL 样例）**。关键是**持续同步 + 反馈闭环 + 版本管理**——一次性建的知识库没意义。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **知识库的核心战略价值是「组织知识的资产化」**——传统 wiki 是给人看的难维护，知识库是**人和 AI 共用**的结构化资产，能让组织知识从"老员工脑子里"沉淀出来
> - **「业务知识」类是知识库最难做的**——表元数据靠平台自动同步，业务流程和概念必须人工沉淀且持续维护，最容易漂移
> - **「典型 SQL 样例」是性价比最高的知识资产**——10~20 个高质量的"问题→SQL"样本能让 RAG 召回质量提升 20%+，比再建多少元数据都管用
> - **回答这题的高分姿势是「分层 + 物理形态 + 持续运营」**——能讲到"知识库不是一次性的"，体现出**真做过且踩过坑**
