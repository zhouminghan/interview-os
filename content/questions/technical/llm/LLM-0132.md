> **来源面经**：阿里系-AI数据工程师两面-20260521 集团2-Q8

这是 Agent 问数从 demo 到生产的最大门槛。难点可以拆成 **5 个层面**：

**1. 元数据召回的精度问题**

- 问题：用户问"近 7 天 GMV"，数仓里**几十张表都有 GMV 字段**（DWD 明细 / DWS 日累计 / ADS 城市维度），AI 选哪张？
- 难点：基础 RAG 召回 Top-K 表，**召回不准就全错**
- 表多了之后向量召回的混淆度急剧上升

**2. 表关联（JOIN）的推理问题**

- 问题：用户问"近 7 天华东区 iPhone 用户的 GMV"——要 JOIN 订单表 + 用户维表 + 设备维表 + 地理维表
- 难点：AI 要**自主推理出 JOIN 路径**——哪张事实表 + 哪些维度表 + 关联字段是什么
- 多跳 JOIN 是 AI 写 SQL 的高错误率场景

**3. 口径歧义问题**

- 问题：用户问"DAU"，三张表都有但口径不同——`dws_user_active_da` 算的是登录、`dwd_user_event` 按事件去重、`ads_user_metric` 走平台标准定义
- 难点：AI 没法分辨**业务方真正想问的是哪个口径**
- 必须靠语义层 + 同义词 + 指标注册中心兜底

**4. 跨域数据组合的语义问题**

- 问题：用户问"内容域和用户域的交叉指标"——AI 要理解两个域怎么关联
- 难点：跨域往往**没有现成的事实表**，AI 要现编 JOIN 逻辑，错误率剧增
- 解决：建跨域 DWS 宽表 + 主动告知 AI 这是跨域指标的"标准答案"

**5. 模糊性问题**

- 问题：用户问"近期"——是 7 天还是 30 天？问"用户"——是新客还是全部？
- 难点：自然语言天然模糊，AI 默认假设可能不符合业务方期望
- 解决：**主动澄清** + **常用默认值** + **多轮对话**

**6. 性能 / 成本问题（隐藏难点）**

- 问题：AI 写出的 SQL 可能扫全表 / 不命中分区 / JOIN 顺序错
- 难点：准确性和性能要同时保证
- 解决：执行前 explain 校验 + 强制分区裁剪 + 资源 quota 兜底

**项目里的应对思路**（虽然 QQ 频道我们还在探索阶段）：
- 把 99 张 DIM 表 + 核心 DWS 宽表的元数据 + 业务语义沉淀到知识库，**让 AI 看治理过的视图而不是原始表**
- 跨域问题先拒绝，引导业务方走 DataTalk 报表
- 关键指标走指标注册中心强一致

**回答模板**：「难点有 6 个层面——**召回精度**（多张同名字段表选哪张）、**JOIN 推理**（多跳关联路径）、**口径歧义**（同概念多口径）、**跨域语义**（没有现成事实表）、**模糊性**（"近期"是几天）、**性能成本**（AI 写的 SQL 性能未优化）。本质是**Agent 问数把数据治理的所有历史债都暴露出来了**——治理欠的债，AI 替你还。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **「Agent 问数 → 暴露治理债务」是 2025 年的共识**——很多公司上 Agent 问数时才发现自己数仓有多乱，反过来推动了元数据治理、指标注册中心的建设。这是个「以攻代守」的好机会
> - **大型数仓的 Agent 问数准确率天花板比小数据集低**——MIT 的 Spider/BIRD 等基准上 Text-to-SQL 准确率能到 80%+，但企业真实数仓（几千张表）通常只到 40~60%。原因就是上面那 5~6 个难点的复合作用
> - **跨域问数是「AI 能力天花板」**——同域查询用 RAG + 语义层能做到不错，跨域要 AI 自主推理 JOIN，目前 LLM 还不够强。生产实践通常是**预先建跨域宽表**绕过这个难点
> - **回答这题的高分姿势是「难点 + 治理本质」**——光列难点像背书，能升华到"Agent 问数 = 数据治理的最终考核"，立刻显示出**架构师视野**
