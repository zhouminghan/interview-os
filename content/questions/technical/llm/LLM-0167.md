我们用的是 **结构化文件存储（Markdown + JSON）**，没有用向量数据库做检查点。原因：

1. **检查点是结构化状态，不是语义信息**。检查点记录的是"第二阶段完成了，产出了这份 DDL，用户确认通过"——这是精确的状态数据，不需要模糊语义检索。向量数据库擅长的是"用户问了一个相关的问题，找到最相似的知识片段"，不适合存精确状态。

2. **可读性和可调试性**。MD 文件 DE 可以直接打开看，出了问题可以手动改状态。向量库里的 embedding 人没法直接阅读和修改。

3. **确定性检索 vs 语义检索**。检查点的读取是"读取上一阶段的产出"——路径确定、内容确定，不需要相似度排序。直接读文件比查向量库更可靠、更快。

向量数据库在项目里的用途是 **知识库的检索**（RAG），不是检查点存储。两者解决的问题不同：
- 知识库 → 模糊匹配 → 向量检索
- 检查点 → 精确读取 → 文件系统
