> **来源面经**：阿里系-AI数据工程师两面-20260521 集团2-Q9

承接上一题（多表问数难点），具体落地要维护 **6 类信息**：

**1. 表级元数据（基础）**
- 表中文名 + 一句话描述 + 业务域归属
- 粒度声明（"一行 = ?"）
- 数据更新频率 + SLA 等级
- 是否是核心推荐表（AI 优先用核心表）

**2. 字段级元数据（精确口径）**
- 字段中文名 + 业务含义 + 计算公式
- 字段值域 / 枚举值（"event_type 取值: click/view/share"）
- 字段使用样例

**3. 表关系图（最关键）**
- 显式定义**哪些表能 JOIN、关联字段是什么、JOIN 类型**（一对一 / 一对多）
- 推荐 JOIN 路径——"算 GMV 时主表用 dwd_trade_order_di，关联用户维度走 dim_user.user_id"
- **跨域关联预定义**——把跨域 JOIN 沉淀成 DWS 宽表

**4. 指标注册中心**
- 标准指标名 + 同义词词典（DAU / 日活 / active_uv 同义）
- 指标计算公式 + 主表
- 指标负责人

**5. 典型查询样例（Few-shot 学习材料）**
- 每张核心表配 5~10 个典型查询 SQL（自然语言问题 + 标准 SQL）
- AI 通过 RAG 召回相似样例做 in-context learning
- **历史用户问答 + 反馈也要沉淀**——越用越准

**6. 常见坑 / 边界条件（避免 AI 翻车）**
- "这张表 user_id 包含游客，要 WHERE user_type='real'"
- "这张表数据 2026-03 之前不准，请用 dt >= '2026-03-01'"
- "这张表 city 字段有 NULL，需要兜底"

**信息维护方式**：
- **结构化沉淀**：YAML / JSON Schema 写死字段、表关系、指标注册
- **自动同步**：从平台元数据 + Git 变更自动更新，避免人工维护漂移
- **持续运营**：建立"问答失败 → 标注 → 反哺知识库"的闭环

**项目里的对应**：我们 QQ 频道用 AI 自动生成的「表知识文件」覆盖了 1、2、6 类，**指标注册中心**对应类 4，类 3「表关系图」是当前最薄弱的环节，类 5「典型 SQL 样例」靠日常 SQL 沉淀积累。

**回答模板**：「6 类信息——**表元数据**（基础）、**字段元数据**（精确口径）、**表关系图**（JOIN 路径，最关键）、**指标注册中心**（同义词 + 标准口径）、**典型查询样例**（Few-shot 材料）、**常见坑**（避翻车）。维护方式靠**结构化沉淀 + 自动同步 + 反馈闭环**——光建一次没用，要让它持续更新。」

> 💡 **专家补充**（大数据架构师视角，面试中视情况展开）
>
> - **「表关系图」是 Agent 问数最被低估的资产**——大多数团队的元数据治理覆盖了表和字段，但**跨表 JOIN 关系**是隐性的（在老员工脑子里）。把它显式化是 AI 时代的硬性要求
> - **典型查询样例的价值远超想象**——RAG 召回历史相似 SQL 比让 LLM 从零写 SQL 准确率高 20~30 个百分点。这是「SQL 沉淀越多越准」的飞轮效应
> - **「持续运营」是知识库的真正难点**——一次性建一个知识库不难，难的是和数仓变更同步、和业务概念演进同步。生产实践通常用**自动同步 + 人工审核**双管齐下
> - **回答这题的高分姿势是「6 类信息 + 维护机制 + 项目薄弱点诚实说**」——能主动讲"我们项目类 3 表关系图是最薄弱的"，反而显示出**真做过 + 有反思**
